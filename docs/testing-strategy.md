# 테스트 전략 및 타당성 평가 보고서

## 핵심 질문

> **"사람이 전수 테스트해야 하는가?"**
>
> **→ 아니요.** 초경량 3계층 자동화 + 인간의 UX 탐색 조합이 최적의 전략이다.

---

## 1. 채택한 테스트 전략: 초경량 3계층 자동화

### 계층 1: pre-push 단위 테스트 (Vitest)

| 항목 | 내용 |
|------|------|
| **도구** | Vitest |
| **실행 시점** | `git push` 전 자동 실행 (pre-push 훅) |
| **대상** | 비즈니스 로직, 유틸 함수, 데이터 변환 |
| **목표** | 핵심 로직의 회귀 방지 |
| **실행 시간** | 10초 이내 |

```bash
# .git/hooks/pre-push
#!/bin/bash
pnpm vitest run --reporter=verbose
if [ $? -ne 0 ]; then
  echo "❌ 단위 테스트 실패 — push 차단"
  exit 1
fi
```

### 계층 2: GitHub Actions CI

| 항목 | 내용 |
|------|------|
| **도구** | GitHub Actions |
| **실행 시점** | PR 생성 및 push 시 자동 |
| **대상** | 전체 테스트 스위트 + 린트 + 타입 체크 + 빌드 |
| **목표** | 통합 환경에서의 전체 검증 |
| **실행 시간** | 2-5분 |

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm type-check
      - run: pnpm test
      - run: pnpm build
```

### 계층 3: Vitest Watch (개발 중)

| 항목 | 내용 |
|------|------|
| **도구** | Vitest (watch 모드) |
| **실행 시점** | 개발 중 상시 |
| **대상** | 변경된 파일과 관련된 테스트만 |
| **목표** | 즉각적인 피드백 루프 |
| **실행 시간** | 변경 감지 후 1-3초 |

```bash
# 개발 중 터미널에서 상시 실행
pnpm vitest --watch
```

### 보조 계층: 경량 E2E (선택적)

| 항목 | 내용 |
|------|------|
| **도구** | Playwright |
| **실행 시점** | 핵심 플로우 변경 시 수동 또는 CI |
| **대상** | 로그인, 핵심 CRUD, 결제 등 크리티컬 패스만 |
| **목표** | 사용자 시나리오 수준의 최소 검증 |
| **실행 시간** | 30초-2분 |

## 2. 인간의 역할: UX 탐색 테스트

자동화가 커버하지 못하는 영역은 **인간이 탐색적으로 검증**한다:

- 시각적 일관성 (다크 모드 전환, 반응형 깨짐)
- 인터랙션 자연스러움 (애니메이션, 트랜지션)
- 비즈니스 흐름의 직관성 (UX 관점)
- 에지 케이스 탐색 (극단적 데이터, 네트워크 오류)

> **인간은 "전수 테스트"가 아니라 "탐색적 테스트"에 집중한다.**

---

## 3. 명시적으로 배제한 전략

### ❌ Chaos Engineering

- **이유**: 소규모 서비스에서는 ROI가 극히 낮음
- **대안**: Docker 컨테이너 재시작 시 복구 확인 수준으로 충분

### ❌ Visual Regression Testing (Percy, Chromatic 등)

- **이유**: 설정·유지 비용 대비 효과 낮음, 잦은 False Positive
- **대안**: 다크 모드 전환 등은 design-qa-inspector 스킬로 수동 검증

### ❌ 80% 커버리지 강제

- **이유**: 커버리지 숫자를 채우기 위한 무의미한 테스트 양산
- **대안**: 비즈니스 로직 중심 선택적 테스트 (커버리지 목표 없음)

### ❌ 전수 UI E2E

- **이유**: 느림(5-15분+), 불안정(Flaky), 유지보수 비용 높음
- **대안**: 크리티컬 패스 5-10개만 E2E, 나머지는 단위 테스트

## 4. 전략 요약 다이어그램

```
비용 ↑
     │
     │  ❌ 전수 UI E2E (배제)
     │  ❌ Visual Regression (배제)
     │  ❌ 80% 커버리지 강제 (배제)
     │
     │  ────────── 채택 경계선 ──────────
     │
     │  ✅ 경량 E2E (크리티컬 패스만)
     │  ✅ GitHub Actions CI (통합)
     │  ✅ pre-push 단위 테스트 (게이트)
     │  ✅ Vitest Watch (개발 중)
     │
     │  🧑 인간 UX 탐색 (보조)
     │
     └─────────────────────────────→ 효과
```

## 5. 결론

| 원칙 | 내용 |
|------|------|
| **자동화** | 빠르고 저렴한 3계층 (단위 → CI → 경량 E2E) |
| **인간** | 탐색적 UX 테스트에 집중 (전수 금지) |
| **커버리지** | 숫자 목표 없음, 비즈니스 로직 중심 |
| **ROI 기준** | 유지보수 비용 > 버그 방지 효과 → 배제 |
