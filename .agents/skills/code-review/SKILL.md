# 🔍 코드 리뷰 전문가 (Code Review Expert)

지정된 검토 범위에 따라 프로젝트의 코드 품질, 구조적 무결성, 보안 및 잠재적 결함을 심층 분석하고, 누구나 이해하기 쉬운 일상적 비유와 함께 GitHub 계층 이슈로 등록하는 표준 코드 리뷰 워크플로우를 제공합니다.

---

## 📌 핵심 원칙 (Core Principles)

1. **범위 명확화 (Scope First)**: 사용자가 프롬프트에서 범위를 지정하지 않은 경우, 추측하지 않고 아래 8가지 범위를 선택하게 한다. 최근 24시간 반영된 변경분을 권장하며, 이미 지정한 범위는 다시 묻지 않는다.
2. **사전 기본 검증 (Verification First)**: 정적 분석 전 프로젝트 기본 검증(타입 체크, 린트 등)을 실행하여 기존 빌드/타입 에러를 먼저 확보한다.
3. **쉬운 설명 필수 (Plain Metaphor First)**: 비개발자나 동료 누구나 문제의 본질을 즉시 이해할 수 있도록 **일상적 비유(Metaphor)를 먼저 제시**한 뒤 기술적 원인과 해결 코드를 설명한다.
4. **결과 문서 저장 금지 (No Local File Clutter)**: 로컬 저장소에 별도 마크다운 리뷰 보고서 파일을 생성하지 않는다. 리뷰 결과는 채팅창에 먼저 보고하고 승인 후 GitHub 이슈로만 등록한다.
5. **계층적 GitHub 이슈 관리 (Hierarchical Issue Tracking)**:
   - 전체를 관할하는 **상위 부모 이슈 1개** 생성 (체크리스트 및 요약 포함)
   - **P0(긴급), P1(주요)**: 건별로 **개별 하위 이슈** 생성
   - **P2(보통), P3(제안)**: **1개의 묶음 하위 이슈**로 통합 생성
   - 상위 부모 이슈와 하위 이슈 간 `#이슈번호` 상호 참조 링크 연결

---

## 🧭 리뷰 범위 (Scope Options)

범위가 명시되지 않았다면 다음 메뉴를 제시한다.

| 번호 | 범위 이름 | 주요 분석 대상 및 관점 |
|---|---|---|
| **1** | **최근 24시간 반영된 변경분 (권장)** | 대상 브랜치에 최근 24시간 동안 반영된 변경의 버그·회귀·보안 문제 |
| **2** | **최근 7일 반영된 변경분** | 리뷰가 밀렸을 때 최근 7일 동안 반영된 변경의 누적 영향 |
| **3** | **특정 PR·커밋·기간의 변경분** | 지정한 PR, 커밋 또는 마지막 리뷰 커밋 이후 등 명시한 비교 범위 |
| **4** | **전체 코드 점검** | 주요 기능, 데이터 흐름, 에러 처리, 보안, 성능, 상태 관리 |
| **5** | **구조·아키텍처 점검** | 디렉터리 구성, 모듈 경계, 책임 분리, 의존성 및 결합도 |
| **6** | **데드코드 점검** | 미사용 import/export, 함수·컴포넌트·파일, 레거시 및 주석 처리 코드 |
| **7** | **리팩토링 점검** | 중복 로직, 복잡한 함수·조건문, 타입 안전성, 가독성 |
| **8** | **AI 개발환경 점검** | AI 에이전트 지침, SSOT, `.agents/`, rules, skills, hooks의 일관성 |

변경분의 '반영'은 일반 merge, squash merge, rebase merge 및 직접 커밋을 포함한다. 미커밋 변경은 사용자가 요청한 경우에만 포함한다.

## 🚦 우선순위 및 심각도 분류 (P Level Standards)

| 등급 | 심각도 | 정의 및 조치 기준 | 이슈 생성 방식 |
|---|---|---|---|
| **P0** | **Critical / Blocker** | 서비스 중단, 데이터 손실, 인증/보안 취약점, 빌드 불가 등 즉각적인 해결이 필요한 결함 | **개별 하위 이슈** 생성 |
| **P1** | **Major** | 핵심 비즈니스 로직 오류, 심각한 성능 저하, 예외 미처리, 주요 사용자 기능 결함 | **개별 하위 이슈** 생성 |
| **P2** | **Minor / Normal** | 코드 냄새, 중복 코드, 사소한 엣지 케이스, 경미한 가독성/타입 경고 | **묶음 하위 이슈 1개**로 취합 |
| **P3** | **Trivial / Suggestion** | 변수 네이밍 제안, 선택적 클린코드 권장사항, 주석 보완 | **P2와 묶음 하위 이슈**로 통합 |

## 🔄 실행 워크플로우

### 1단계: 범위 확정
- 프롬프트에 범위가 명시되어 있다면 해당 범위로 즉시 확정한다.
- 범위가 없다면 위 메뉴를 제시하고 선택받는다. 1번을 권장하되 응답 없이 선택을 확정하지 않는다.
- 변경분 리뷰는 사용자 지정 브랜치를 우선하고, 지정이 없으면 저장소의 기본 브랜치를 확인하여 사용한다.
- 4번부터 8번은 지정한 폴더·모듈을 대상으로 하며, 별도 지정이 없으면 프로젝트 전체에 해당 관점을 적용한다.

### 2단계: 사전 기본 검증 (Pre-Flight Checks)
프로젝트 환경에 맞는 빌드/린트/타입체크 명령을 먼저 실행하여 잠재 에러를 수집한다:
- 실행 실패 시 에러 로그를 리뷰 대상 항목(P0/P1)에 우선 반영한다.

### 3단계: 범위별 심층 분석 수행

#### 1·2. 최근 24시간·7일 반영된 변경분
- 대상 브랜치의 최신 원격 상태를 확인한다. 원격 조회가 불가능하면 로컬 참조의 한계를 보고한다.
- 리뷰 시작 시각을 고정하고 시간대가 포함된 시작·종료 시각, 대상 브랜치, 종료 커밋 SHA를 기록한다.
- 대상 브랜치의 **first-parent 이력과 커미터 시각**으로 기간 내 반영된 커밋을 선택한다.
- 일반 merge는 merge 커밋과 첫 번째 부모의 diff로 변경을 확인한다. squash·rebase·직접 커밋도 각 커밋과 첫 번째 부모를 비교한다.
- 변경 코드와 영향받는 호출부·관련 테스트를 중심으로 확인한다.
- 이번 변경에서 생긴 문제와 기존 문제를 구분하여 보고한다.
- 기간 내 대상 변경이 없으면 그 사실을 보고하고 종료한다. 임의로 기간이나 브랜치를 확대하지 않는다.

#### 3. 특정 PR·커밋·기간의 변경분
- PR은 지정된 PR의 base/head 및 변경 diff를 확인한다.
- 단일 커밋은 첫 번째 부모와 비교하고, 명시한 두 커밋은 지정된 기준에 따라 비교한다.

#### 4. 전체 코드 점검
- 핵심 비즈니스 로직, 데이터베이스 쿼리, API 라우트와 데이터 흐름을 검토한다.
- 에러 처리 누락, 리소스 누수, 보안 위험 및 성능 병목을 점검한다.
- 실제 검토한 영역과 미검토 영역을 보고하여 전체 코드의 무결성을 보장한 것으로 오해하지 않게 한다.

#### 5. 구조·아키텍처 점검
- 디렉터리 구성, 모듈 의존성, 관심사·책임 분리 및 계층 경계를 조사한다.
- 순환 의존성, 과도한 결합도와 기능 변경 시 여러 모듈로 수정이 번지는 구조를 점검한다.

#### 6. 데드코드 점검
- 프로젝트에 설치된 분석 도구와 `rg`를 활용해 미사용 import/export, 파일, 함수를 탐색한다.
- 프레임워크의 파일 기반 라우팅, 동적 import, 문자열 참조 및 외부 호출 가능성을 확인한 후 미사용으로 판단한다.

#### 7. 리팩토링 점검
- 긴 함수, 반복 로직, 깊은 중첩, 복잡한 조건문 및 타입 안전성 결여를 조사한다.
- 길이·반복 횟수만으로 결함을 확정하지 않고 실제 유지보수 비용과 변경 위험을 근거로 개선을 제안한다.

#### 8. AI 개발환경 점검
- `.agents/`, `.gemini/`, rules, skills, hooks 및 에이전트 지침의 일관성을 조사한다.
- SSOT, 심볼릭 링크의 실제 원본, 중복·충돌 지침과 유효하지 않은 경로를 점검한다.

### 4단계: 쉬운 설명(비유) 작성 규칙

모든 발견 항목은 아래 구조를 엄격히 준수하여 기술한다:

> **[비유로 이해하기]**
> *"마치 식당에서 요리사가 주문 접수, 요리, 서빙, 결제, 설거지까지 혼자 다 처리하느라 손님이 몰리면 가게 전체가 멈추는 상황과 같습니다."*
> **[기술적 원인]**
> 단일 함수 내에서 여러 책임이 결합되어 단일 책임 원칙(SRP)을 위반하고 있습니다.
> **[위치]** `src/services/order.ts#L45-L120`
> **[해결 방안]** 알림 발송과 재고 차감을 이벤트 핸들러로 분리하여 비동기 처리합니다.

### 5단계: 채팅창 보고 및 승인 요청 (No Auto-Create)
- 분석 결과를 심각도별(P0 -> P1 -> P2 -> P3)로 정리하여 채팅창에 출력한다.
- **절대로 승인 없이 바로 GitHub 이슈를 생성하지 않는다.**
- 사용자에게 GitHub 이슈 등록 진행 여부를 확인한다:
  > *"코드 리뷰 분석을 마쳤습니다. 위 결과를 바탕으로 상위 부모 이슈 1개 및 P 레벨별 하위 이슈들을 GitHub에 등록할까요?"*

### 6단계: GitHub 계층 이슈 생성 (승인 후)
`github-issue` 스킬의 규칙에 따라 계층 이슈를 생성한다:

1. **상위 부모 이슈 생성 (1개)**:
   - 제목: `[Code Review] <검토 범위 이름> 코드 리뷰 결과 종합`
   - 내용: 전체 개요, 검토 범위, 통계(P0: X건, P1: Y건, P2/P3: Z건), 하위 이슈 체크리스트 (자리표시자)
   - 생성 즉시 상위 이슈 번호(`#PARENT_ID`) 확보

2. **P0 / P1 개별 하위 이슈 생성**:
   - 제목: `[P0] <문제 요약>` 또는 `[P1] <문제 요약>`
   - 본문: 상위 이슈 링크(`상위 이슈: #PARENT_ID`), 쉬운 비유 설명, 기술적 원인, 대상 코드 링크, 개선 권장 코드
   - 생성 즉시 하위 이슈 번호 확보

3. **P2 / P3 묶음 하위 이슈 생성 (1개)**:
   - 제목: `[P2/P3] <검토 범위 이름> 코드 품질 및 가독성 개선 항목`
   - 본문: 상위 이슈 링크, 각 P2/P3 항목별 체크리스트, 쉬운 비유 한 줄 요약, 파일 위치

4. **상위 부모 이슈 업데이트**:
   - 부모 이슈 본문 또는 댓글에 생성된 하위 이슈 번호들을 체크리스트 링크(`- [ ] #<번호> <제목>`)로 연결 등록

## ⚠️ 주의 사항 및 금기 사항 (Strict Constraints)

- ❌ **로컬 문서 파일 생성 절대 금지**: 저장소 파일로 결과를 남기지 않는다.
- ❌ **임의 라벨 생성 금지**: 프로젝트 허용 라벨만 사용한다.
- ❌ **단독 기술 용어 나열 금지**: 비유 설명 없이 기술 용어로만 된 불친절한 설명을 등록하지 않는다.
- ❌ **승인 없는 이슈 자동 생성 금지**: 반드시 사용자 승인 후 GitHub 이슈를 생성한다.
