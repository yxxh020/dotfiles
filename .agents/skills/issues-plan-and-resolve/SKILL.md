# 이슈 계획 수립 & 일괄 해결 스킬

## 트리거 조건

다음 요청이 들어오면 이 스킬을 즉시 활성화한다:

- "이슈 확인해서 계획 댓글 달아줘"
- "이슈 전체 작업 진행해줘" / "계획대로 모두 처리해줘"
- "이슈 전수 분석해줘"

> **두 단계 요청** 구분:
> - **계획만**: Phase 1~2 실행 후 반드시 중단. 명시적 승인 없이 Phase 3 진입 금지.
> - **전체 처리**: Phase 3~5 실행 (계획 댓글이 이미 있으면 분석 생략).

---

## 핵심 원칙

- **분석은 병렬, 수정은 순차.**
- 같은 파일을 건드리는 이슈들은 반드시 순서를 결정하고 순차 처리한다.
- **커밋 게이트는 테스트 러너 종료 코드(exit code 0)로만 판단.** 파이프(`|`)로 가리지 않는다.
- push는 사용자의 명시적 요청이 있을 때만 수행한다.

---

## Phase 1: 이슈 수집

```bash
git remote -v                                                        # 올바른 저장소 확인
gh issue list --state open --json number,title,body --limit 50      # 전수 조회
```

- 기존 점검 리포트나 감사 결과가 있으면 먼저 읽어 분석 비용 절감.
- 연관 이슈끼리 묶어 의존 관계를 파악한다.

---

## Phase 2: 계획 댓글 등록

각 이슈에 아래 형식으로 댓글 작성 (`gh issue comment N --body-file <파일>`):

```
**처리 방향**: 핵심 접근 (파일:라인 근거)
**수정 대상**: 파일 목록
**작업 단계**: 3~5단계
**의존 관계**: 선행 이슈, 같은 파일을 수정하는 이슈
**예상 작업량**: S/M/L
```

> **안전 규칙**: 본문은 heredoc(`<<'EOF'`)으로 임시 파일에 쓰고 `--body-file`로 등록.
> 따옴표/백틱 이스케이프 사고를 원천 차단한다.

- 댓글 등록 후 **의존 그래프와 권장 작업 순서**를 사용자에게 보고.
- 계획만 요청한 경우 **여기서 중단**. 처리 지시가 있을 때만 Phase 3 진행.

---

## Phase 3: 실행 준비

처리 순서 결정 원칙:

1. 테스트 인프라 (없으면 0순위로 도입)
2. 최소 수정 (워밍업)
3. 의존 관계 순서 — 같은 코드를 만지는 이슈는 선행 이슈부터
4. 독립 이슈들
5. 광역 리팩토링 (여러 모듈을 건드리는 것)
6. **문서 동기화는 맨 마지막** (기능 확정 후 재수정 없도록)

---

## Phase 4: 이슈별 처리 루프 및 실시간 브리핑

각 이슈에 대해:

1. **RED** → 실패 테스트 먼저 작성, 실패 확인
2. **GREEN** → 통과시키는 최소 수정
3. **커밋 게이트** — exit code 0 확인 후에만 커밋
   ```bash
   <프로젝트 테스트 러너>; echo "EXIT=$?"
   git add <명시적 경로> && git commit -m "feat: #N 설명"
   ```
4. **이슈 close** — `gh issue close N --comment` + 커밋 해시(반드시 `git log -1 --format=%h`로 확보)
5. ⚡ **이슈 해결 브리핑 및 자동 진행 (Auto-Continue)**:
   - 각 이슈 처리 완료(또는 2회 실패) 즉시 아래 브리핑을 실시간 출력하고, 사용자 입력 대기 없이 즉시 다음 이슈로 자동 진행한다.

```markdown
---
## 📌 이슈 해결 브리핑 — Issue #N

### 🔍 이슈 내용 및 결함 요약
- **이슈 번호**: #N (`이슈 제목`)
- **결함/요구사항**: 이슈 핵심 문제 및 현상 요약

### 🛠 수정 조치 리스트
| # | 수정 파일 (`파일:라인`) | 변경 내용 상세 |
|---|----------------------|--------------|
| 1 | `src/path/file.ts:42` | 버그 픽스 또는 기능 구현 상세 |

### 💡 원인 분석 및 설명
- **원인/배경**: 버그 발생 원인 또는 스펙 구현 배경
- **해결 방식**: 적용한 설계/로직 및 방어 전략

### ⏩ 다음 단계
> [자동 진행] 다음 이슈(#M) 해결 착수 (또는 Phase 5 마무리 진입)
---
```

6. 실패 시: 1회 재시도 → 2회 실패 시 failed 기록 후 다음 이슈로 자동 진행.

---

## Phase 5: 마무리

- 전체 테스트 실행
- 결과 요약표 출력 (이슈·상태·커밋, 완료/실패 수)
- 검증 불가 항목은 명시적으로 한계 보고
- push/merge는 사용자의 명시적 요청 시에만

---

## 흔한 실수 (Common Mistakes)

| 실수 | 방지책 |
|---|---|
| close 댓글에 `{HASH}` 플레이스홀더 그대로 등록 | 커밋 먼저 완료 후 `$(git log -1 --format=%h)` 삽입 |
| `pytest \| tail` 파이프로 exit code 가려짐 | 게이트 판정은 파이프 없이, `; echo "EXIT=$?"` 확인 |
| 같은 파일 수정 이슈를 임의 순서로 처리 | Phase 2에서 파일 충돌 쌍 식별 후 반드시 순차 |
| 문서 동기화를 기능 구현 전에 처리 | 문서 이슈는 항상 마지막 |
| "이 이슈는 간단하니 테스트 없이" | 테스트 인프라가 있는 한 RED 먼저 |
