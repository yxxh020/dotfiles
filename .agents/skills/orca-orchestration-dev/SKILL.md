# Orca 오케스트레이션 개발 워크플로우

PRD 또는 기획 내용을 받아 **감독형 멀티 에이전트 개발**로 구현하는 절차.

## 적용 범위

이 스킬은 개발 구간에만 쓴다.

| 구간 | 단계 | 이 스킬 |
|---|---|---|
| 기획 | 환경 세팅 · 서비스 조사 · 기획 · 화면 설계 · PRD | ❌ 일반 대화 |
| **개발** | **기술 설계 · Task 쪼개기 · 구현 · 통합 · 점검** | ✅ **이 스킬** |
| 배포 | 배포 준비 · 배포 | ❌ 사용자가 직접 |

**배포는 절대 대행하지 않는다.** 되돌리기 어렵고 실사용자에게 영향이 간다.

## 쓰지 말아야 할 때

아래에 해당하면 오케스트레이션을 쓰지 말고 일반 작업으로 처리하라고 사용자에게 알린다.

- 수정할 파일이 1~2개
- Task로 쪼갤 것이 3개 미만
- 빌드가 매우 무거워 워커들이 빌드 자원을 두고 계속 충돌하는 프로젝트
- "넘겨줘 / handoff / 다른 에이전트에게 줘" 요청 — 이건 소유권 이전이며 감독형이 아니다

## 실행 절차

### STEP 0 — 스킬·런타임 로드 (생략 금지)

```bash
orca skills get orchestration --full
orca agent-context --json
orca status --json
orca orchestration task-list --json
orca terminal list --json
```

- `skills get`과 `agent-context`가 **이 빌드의 유일한 정답지**다. 웹 문서(onorca.dev/docs)와 명령 체계가 다르므로 문서나 기억으로 명령을 구성하지 않는다.
- `--help`에 없는 플래그가 `agent-context`에는 있다. 반드시 둘 다 읽는다.
- `task-list`에 이전 회차 잔여물이 있으면 사용자에게 알린다. `reset`은 런타임 전역이므로 **먼저 실행하지 않는다.**

### STEP 1 — 환경 조사 (생략 금지)

Task를 쓰기 **전에** 조사한다. 이 단계를 빼면 spec이 환경에서 실현 불가능해 해당 Task가 전건 실패한다.

조사 항목:

1. `package.json`(또는 해당 언어의 의존성 파일)의 실제 설치 목록 — **없는 라이브러리 확인이 목적**
2. 테스트 러너·environment·include 패턴·설치된 어댑터
3. 빌드/타입체크 명령의 실제 이름
4. 폴더 구조와 공유되는 파일
5. 여러 워커가 동시에 쓰면 충돌할 자원 (빌드 캐시, 포트, 락파일)

조사 결과를 근거로 **사용자 요구 중 현재 환경에서 불가능한 항목을 먼저 지적**한다. 추측으로 완료 조건을 쓰지 않는다.

### STEP 2 — Task DAG 설계 + 전체 생성

#### 표준 Task 구조

```
T1 계약 확정 (deps 없음)
     │
  ┌──┴──┐          ← 동시 실행
 T2    T3
  └──┬──┘
     ▼
   T통합 → T점검
```

| Task | 역할 | 필수 제약 |
|---|---|---|
| **첫 Task: 계약 확정** | 데이터 구조·타입·API 요청/응답 형식을 확정하고 문서화 | **구현 금지.** 이 파일은 첫 Task만 수정 가능 |
| 중간 Task들 | 기능 구현 | 계약을 바꾸지 마. 계약 파일은 읽기만 |
| 뒤에서 두 번째: 통합 | 스타일·이름 규칙 통일 | 기능 변경 금지 |
| 마지막: 점검 | 테스트 작성·실행 | **소스 수정 금지.** 문제는 보고만 |

**첫 Task가 병렬의 전제다.** 공유 타입·계약을 한 Task가 먼저 확정하고 잠그면, 이후 Task들은 읽기만 하므로 동시 실행이 가능해진다. 이걸 빼면 병렬 작업이 서로 다른 형식을 가정해 합칠 때 전부 뜯어야 한다.

#### 파일 소유권 배정 (필수)

격리는 워크트리가 아니라 **파일 단위 배타 소유**로 달성한다.

- Task마다 `쓰기 허용` 파일 목록을 명시한다
- 나머지는 `읽기만`으로 둔다
- **미할당 파일 목록을 반드시 적는다** — 공유 컴포넌트, 의존성 파일, 빌드 설정. 워커가 이걸 건드려야 할 때 `ask`가 올라온다
- 할당 외 파일 수정이 필요하면 `ask` 또는 `escalation`을 쓰라고 spec에 적는다

#### spec 작성 원칙 5개

| # | 원칙 |
|---|---|
| 0 | STEP 1 조사 결과에 근거해 쓴다. 없는 라이브러리·불가능한 테스트 방식을 전제하지 않는다 |
| 1 | 위치는 애매어("바로 다음") 대신 행 번호·리터럴로 |
| 2 | 최종 상태를 리터럴 블록으로 명시 |
| 3 | 금지 사항 명시 — 문자 단위 무수정 / 타 파일 무접촉 / 커밋 금지 / 새 의존성 추가 금지 |
| 4 | **완료 조건을 "통과해야 하는 명령"으로 쓴다** — 가장 강력함 |

원칙 4의 효과: 검증 명령을 spec에 넣으면 워커가 검증 가능한 구현 전략으로 바꾼다. (실측 사례: `diff <(git show HEAD:F \| sort) <(sort F)` 출력이 비어야 한다는 조건을 걸자 워커가 텍스트 재작성 대신 행 순열 재조립을 택해 문자 변형 가능성을 구조적으로 제거함)

#### Task 생성

- **DAG 전체를 한 번에 생성한다.** 이 빌드에서 `ready` 승격은 선행 Task 완료 시점의 이벤트로만 발생하고 소급 계산되지 않는다. 이미 완료된 Task에 `--deps`를 걸면 영구히 `pending`에 머문다
- Task는 5개 이하. 의존성 체인은 3~4단계 이하
- `--task-title`로 사이드바 표시명도 붙인다
- 새 워크트리는 만들지 않는다. 전부 현재 워크트리 + 워커별 새 에이전트 터미널

#### 계획 승인 게이트 (필수)

**dispatch 전에 계획을 사용자에게 제시하고 멈춘다.** 계획에 포함할 것:

1. Task 목록 + 의존성 + 웨이브 구성
2. Task별 담당 워커와 이유
3. 파일 소유권 매트릭스 + 미할당 목록
4. 사용자 판단이 필요한 지점(결정 게이트 후보)
5. 예측되는 위험 (동시 사용 자원 충돌 등)

### STEP 3 — 프리앰블 검수

실제 dispatch 전에 dry-run으로 주입될 지시서를 확인한다.

```bash
orca orchestration dispatch --task <id> --to <handle> --dry-run --return-preamble --json
```

검수 4항목:

| # | 확인 | 실패 시 |
|---|---|---|
| 1 | `worker_done` 전송 명령 포함 | 완료 보고가 오지 않음 |
| 2 | `taskId`가 실제 값 | dispatch 실패 |
| 3 | 코디네이터 핸들이 구체적 (그룹 주소 아님) | 완료 권한 성립 안 함 |
| 4 | TASK 블록에 spec 온전 | 워커가 딴 일을 함 |

- `--dispatch-id ctx_dryrun`은 정상 (플레이스홀더)
- dry-run은 상태를 바꾸지 않는다. `dispatch: null`, `injected: false`로 확인
- **한 번 `--inject`하면 되돌릴 수 없다.** 검수는 여기서 한다

### STEP 4 — 게이트 처리

결정 게이트가 있으면 **4단계 순서를 지킨다.**

```
1. gate-create → gate-resolve            결정 확정
2. 워커에게 확정문 릴레이                 "아직 작업하지 말고 접수만 하라"
3. 워커의 접수 확인                       한 줄 응답 대기
4. 정식 dispatch --inject                 여기서 작업 시작
```

**`--inject` 프리앰블은 게이트 해소 내용을 싣지 않는다.** `task-update`에 `--spec`도 없어 사후 수정이 불가능하다. dispatch 후에 보내면 워커가 이미 미확정 지침으로 일을 시작한 상태다.

보완책: Task spec에 "이 항목은 게이트 확인 중이며 dispatch 시점의 확정 지침을 따를 것"을 미리 박아둔다.

### STEP 5 — 감독

```bash
orca orchestration check --wait --types worker_done,escalation,decision_gate --timeout-ms 900000 --json
```

- `--types`에 **`heartbeat`를 넣지 않는다** — 넣으면 5분마다 대기가 깨진다
- 웹 문서의 `question`은 이 빌드에 없다. `decision_gate`가 맞다
- **타임아웃과 `{count:0}`은 실패가 아니라 체크포인트다.** 코딩 작업은 15~60분이 정상. 롤링 대기를 계속한다
- liveness는 `terminal read` 또는 `terminal wait --for tui-idle`로 확인
- 하트비트나 터미널 활동이 있으면 워커를 **중단·재시작하지 않는다**
- **`check --wait`는 한 번에 1건만 반환한다.** 워커 N개가 동시에 끝날 수 있으면 N번 루프를 돈다. 한 건만 처리하고 다음 웨이브로 넘어가면 후속 Task가 갇힌다
- `decision_gate`가 오면 원문 그대로 사용자에게 전달하고, 답을 `reply`로 넘긴다
- 웨이브 전환 시 `task-list --ready`로 승격을 확인한다

### STEP 6 — 독립 검증 (생략 금지)

**워커 보고를 그대로 신뢰하지 않는다.** 코디네이터가 직접 실행해 확인한다.

| 검증 | 명령 |
|---|---|
| 타입 | 프로젝트의 타입체크 명령 |
| 테스트 | 프로젝트의 테스트 명령 |
| 빌드 | 프로젝트의 빌드 명령 |
| 변경 범위 | `git status`, `git diff --numstat` |
| 소유권 준수 | 미할당 파일에 `git diff -- <file>`로 0줄 확인 |

워커가 "안 건드렸다 / 무손실이다"를 주장하면 그것을 증명하는 명령을 직접 돌린다.

`worker_done` 수신 후 `task-update --status completed`를 **추가하지 않는다.** 유효한 `worker_done`은 자동 전이시킨다.

### STEP 7 — 커밋

- 워커에게는 커밋을 금지시키고 코디네이터가 통합한다
- **웨이브별로 분리 커밋한다.** 각 커밋에 해당 Task의 쓰기 허용 파일만 들어가므로 소유권이 이력에 남는다
- 커밋 메시지에 "무엇"이 아니라 **"왜"** 를 남긴다 — 게이트 결정, 재사용한 공용 함수, 수정하지 않은 이유
- push는 사용자 승인 없이 하지 않는다

## 절대 규칙 요약

1. 사용자에게 `orca orchestration check`를 플래그 없이 치지 말라고 알린다 (미읽음 메시지를 소비해 코디네이터가 영원히 대기하게 됨). 조회는 `inbox` 또는 `--peek` / `--all`
2. 감독 의도를 명시한다 — "감독", "worker_done까지 대기", "DAG 조율" 중 하나가 없으면 handoff로 분류되어 상태가 생성되지 않는다
3. 새 워크트리를 기본으로 쓰지 않는다
4. DAG 전체를 dispatch 전에 생성한다
5. 게이트 결정은 dispatch 전에 릴레이하고 접수를 확인한다
6. `--types`는 `worker_done,escalation,decision_gate`
7. 타임아웃은 실패가 아니다
8. `ask`(워커→코디)와 `gate-create`(코디→사용자)는 방향이 반대다
9. `worker_done` 후 수동 completed 업데이트를 하지 않는다
10. `reset`은 런타임 전역이다. 사용자가 명시적으로 폐기를 요청할 때만
11. 워커에게 `AskUserQuestion`을 쓰게 하지 않는다 — 코디네이터가 볼 수 없어 세션이 영구 정지한다. 프리앰블이 이미 금지하고 있으니 유지한다
12. 배포는 대행하지 않는다

## 사용자에게 보고할 형식

작업 종료 시 아래를 표로 정리한다.

- Task별 상태 전이 로그 (시각 포함)
- 웨이브 구성과 dispatchId
- `failure_count`, escalation·ask 건수
- 독립 검증 결과 (명령별 exit code / 테스트 통과 수)
- 변경 파일 목록 + 미할당 파일 침범 여부
- 남은 판단 사항 (커밋, 워커 터미널 정리 등)

수치와 근거를 함께 제시하고, 검증하지 못한 항목은 "미확인"으로 명시한다.
