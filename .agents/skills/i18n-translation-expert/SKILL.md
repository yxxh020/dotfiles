# i18n 번역 전문가

이 스킬은 프론트엔드의 모든 국제화 작업을 다룬다: next-intl 설정, 메시지/사전 파일 관리, 로케일 인식 라우팅, 양방향 패리티 적용.

## 1. 역할과 전문 영역

`next-intl`을 사용하는 Next.js App Router i18n에 깊은 전문성을 갖춘 시니어 프론트엔드 엔지니어로서 행동한다. 주요 책임: 사용자에게 표시되는 모든 문자열이 지원되는 모든 로케일로 번역되어 있는지 확인하고, 번역 시스템을 일관되게 유지하며, 컴포넌트에 하드코딩된 문자열이 없도록 한다.

## 2. 로케일 설정

> 프로젝트에 맞게 아래 값을 커스터마이징한다:

- **기본 로케일:** `<your-default-locale>` (예: 한국어는 `kr`, 영어는 `en`)
- **지원 로케일:** `['en', '<your-locale>']` — `src/i18n/routing.ts`에 정의
- **URL 패턴:** `localePrefix: 'always'` — 모든 URL에 접두어 포함 (예: `/kr/...` 또는 `/en/...`)
- **라우트 세그먼트:** `src/app/[locale]/...`

## 3. 번역 저장소 구조

문자열을 추가하거나 편집하기 전에, 대상 컴포넌트가 이미 어떤 번역 시스템을 사용하는지 파악하고 일관성을 유지한다.

### System A — `messages/` (next-intl이 요청 시 로드)

```
messages/
├── en/
│   ├── admin.json
│   └── public.json
└── <locale>/
    ├── admin.json
    └── public.json
```

- `src/i18n/request.ts`에서 활성 로케일에 따라 로드된다.
- `useTranslations('namespace.key')` 또는 `getTranslations()`(서버 컴포넌트)로 사용한다.
- **분리 규칙:** 어드민 문자열은 `admin.json`, 공개 문자열은 `public.json`에 넣는다.

### System B — `src/translations/` (레거시 또는 보조)

프로젝트에 레거시 번역 저장소가 있는 경우, 파일명 규칙을 확인하고 단일 컴포넌트 내에서 System A와 혼용하지 않는다.

> 세 번째 시스템을 도입하지 않는다. 어느 것을 사용할지 모르겠으면 대상 컴포넌트를 읽고 기존 import에 맞춘다.

## 4. 핵심 규칙

1. **사용자에게 표시되는 하드코딩 문자열 금지.** 모든 표시 문자열은 번역 파일에서 가져와야 한다.
2. **로케일 패리티.** 한 로케일에 존재하는 모든 키는 같은 구조로 다른 모든 로케일에도 존재해야 한다.
3. **키를 안정적으로 유지한다.** 번역 키 이름 변경은 파괴적 변경이다 — 동일 커밋에서 모든 소비자와 로케일 파일을 함께 업데이트한다.
4. **어드민 vs 공개 분리 (System A).** 라우트 표면에 맞는 파일에 문자열을 넣는다.
5. **네임스페이스 깊이.** 명확한 최상위 네임스페이스(예: `nav`, `modals`, `forms`)로 얕은 구조를 선호한다.
6. **로케일 인식 내비게이션.** 기본 `next/link` 대신 `src/i18n/navigation.ts`의 헬퍼(`Link`, `useRouter`, `usePathname`)를 사용한다.

## 5. 일반적인 작업 처리 방법

### 새 사용자 표시 문자열 추가
1. 올바른 네임스페이스와 표면(어드민 vs 공개)을 결정한다.
2. 모든 로케일 파일에 키-값 쌍을 추가한다.
3. 컴포넌트에서 `const t = useTranslations('namespace')`를 사용하고 `t('key')`로 참조한다.
4. 패리티 확인: 모든 로케일 파일이 같은 키 세트로 변경되었는지 확인한다.

### 새 로케일 추가
1. `src/i18n/routing.ts`의 `locales`에 새 로케일 코드를 추가한다.
2. `src/i18n/request.ts`에 해당 import와 함께 `case` 브랜치를 추가한다.
3. 전체 키 세트를 포함한 `admin.json`과 `public.json`으로 로케일 디렉터리를 생성한다.

### 컴포넌트를 레거시 시스템에서 next-intl로 이관
1. 컴포넌트가 레거시 번역 파일에서 읽는 모든 문자열을 파악한다.
2. 각 문자열을 논리적인 네임스페이스 하에 올바른 `messages/<locale>/<surface>.json`으로 이동한다.
3. 레거시 import를 `useTranslations('namespace')`로 교체한다.
4. 레거시 파일에서 더 이상 사용되지 않는 키를 제거한다.
5. 앱을 실행하고 모든 로케일 경로가 올바르게 렌더링되는지 시각적으로 확인한다.

## 6. 흔한 함정과 엄격한 규칙 (필수 숙지)

1. **로케일 코드 vs 파일명 불일치:** 로케일 코드가 `kr`인데 레거시 파일이 `ko.json`을 사용한다면, 잘못된 파일을 편집하지 않는다. `request.ts`에서 실제 파일을 추적한다.
2. **항상 컴포넌트 import 확인:** `useTranslations(...)`를 사용하면 System A이다. `messages/<locale>/`을 업데이트한다.
3. **맹목적인 전역 찾기-바꾸기 금지:** 먼저 라우팅 설정(`request.ts`)을 이해한다.

## 7. 운영 지침

1. 구조적 변경 전 `src/i18n/routing.ts`와 `src/i18n/request.ts`를 먼저 읽는다.
2. 키 추가 전 모든 로케일 메시지 파일을 검색하여 다른 네임스페이스에 이미 존재하지 않는지 확인한다.
3. 코드와 주석은 영어로만 작성한다.
