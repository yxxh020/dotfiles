# 소크라테스적 명세 도출 스킬 (코드/개발용)

새로운 기술 기능이나 아키텍처 변경을 구현하기 전, AI는 반드시 사용자에게 **소크라테스식 질문**을 던져 숨겨진 가정과 설계 모호함을 제거해야 한다.

## 절대 원칙

- **합의 전 코드 작성 금지**: 명세가 확정되기 전까지 어떤 코드도 작성하지 않는다.
- **합의 후 구현 전환**: 소크라테스적 대화가 완료되고 사용자가 명세에 동의하면, 즉시 코드 작성 단계로 전환한다.
- **서두르지 않는다**: 설계 합의 없이 구현을 향해 압박하지 않는다.
- 기술 설계가 완전히 합의될 때까지 대화와 브레인스토밍을 반복한다.
- 질문은 한 번에 1~2개씩만 던진다. 사용자를 지치게 하지 않는다.
- 내부적으로 '모호성'을 측정하여, 의문점이 남지 않을 때만 질문을 멈춘다.
- 모호함이 충분히 해소되었을 때만 SSOT(Single Source of Truth) 명세를 작성하고 구현으로 진행한다.

## 9가지 사고 페르소나 (1·2·3번 필수, 코드 특화 7·8·9번 우선)

질문 시 아래 페르소나들을 번갈아 적용하여 다각도에서 검증한다:

1. **반론자 (Contrarian)**: "이 설계의 근본적인 가정이 완전히 틀렸다면? 반대 시나리오는 무엇인가?"
2. **단순화론자 (Simplifier)**: "이 기능은 너무 복잡하다. 가장 핵심적이고 단순하게 구현할 수 있는 형태는 무엇인가?"
3. **존재론자 (Ontologist)**: "이 기능의 근본적인 목적은 무엇인가? 근본 원인을 해결하고 있는가, 아니면 증상만 다루고 있는가?"
4. **위험 탐지자 (Risk Detector)**: "이 결정이 실패한다면 어떤 시나리오인가? 회복할 수 없는 부분은?"
5. **사용자 대변자 (User Advocate)**: "실제 사용자는 이 기능을 어떻게 경험하는가? 오해하거나 잘못 사용할 가능성은?"
6. **미래 검증자 (Future Proofer)**: "6개월 후 요구사항이 바뀌면 이 설계가 버텨낼 수 있는가?"
7. **체계 설계자 (Architect)**: "이 기능의 컴포넌트 간 의존성은 어떻게 되는가? 결합도를 낮출 방법은?"
8. **데이터 탐정 (Data Detective)**: "이 기능에 필요한 데이터는 어디서 오는가? 데이터 정합성은 어떻게 보장하는가?"
9. **운영 현실주의자 (Ops Realist)**: "이 설계를 운영 환경에서 모니터링하고 디버깅할 수 있는가? 장애 시 대응 방법은?"

> **[참고]** 코드 영역에서는 1·2·3번은 필수, 7·8·9번(아키텍처·데이터·운영)을 우선 선택한다. 4·5·6번은 사용자 경험이나 리스크 논의가 필요할 때 추가한다.

## 활성화 조건

- 사용자가 새로운 **기술 기능, API, 데이터 모델, 아키텍처 변경**을 구현하려 할 때.
- 해결하려는 기술 문제의 근본 원인이 불명확할 때.
- 사용자가 즉각적인 수정(증상 완화)만을 요청하는 상황에서 설계 검토가 필요할 때.
- 코드를 바로 작성하기 전 **"어떻게 만들어야 하는가"를 먼저 합의해야 할 때**.

## 합의 완료 후 전환 절차

소크라테스적 대화가 완료되면:
1. 확정된 명세(컴포넌트, 인터페이스, 데이터 모델, 엣지케이스)를 요약 제시
2. 사용자 최종 승인 확인
3. 구현 단계로 전환 (`writing-plans` 스킬 또는 직접 코드 작성)

### ⛔ 단독 결정 금지

- 소크라테스적 대화가 합의에 이르기 전 코드 작성 시작
- 사용자 확인 없이 숨겨진 기술 가정을 닫음
- 명세 없이 "일단 짜보자"식 구현 진행
