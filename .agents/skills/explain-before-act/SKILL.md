# explain-before-act — 작업 전 상황 설명 스킬

AI 에이전트가 무작정 코드를 수정하거나 명령어를 실행하지 않고,
반드시 **현재 상황 파악 → 계획 공유 → 사용자 확인(또는 짧은 브리핑) → 실행** 순서를 따르도록 강제하는 행동 규칙이다.

## 언제 적용하는가

아래 상황 중 하나라도 해당하면 이 스킬을 활성화한다:

- 사용자가 새로운 작업(기능 개발, 버그 수정, 리팩토링 등)을 요청할 때
- 여러 파일에 걸쳐 변경이 필요한 작업
- 이전 컨텍스트 없이 처음 접하는 코드베이스·기능 영역
- 작업 범위가 모호하거나 영향 범위가 넓을 때
- 사용자가 "먼저 설명해줘", "상황 파악해줘", "어떻게 할 건지 말해줘"라고 요청할 때

## 실행 순서

### Phase 0 — 침묵 파악 (Silent Research)

사용자에게 보고 전에 내부적으로 다음을 수행한다. **이 단계에서는 파일 수정·명령 실행을 금지한다.**

1. 관련 파일 열람 및 코드 구조 파악
2. 오류 메시지·스택 트레이스 분석 (있는 경우)
3. 영향 범위(변경 필요 파일 목록) 추정
4. 해결 접근법 2-3가지 검토

### Phase 1 — 상황 브리핑 (Situation Briefing)

사용자에게 다음 항목을 **간결하게** 보고한다:

```
## 🔍 상황 파악

**현재 문제:**
[오류/이슈/요청을 한 줄로 요약]

**원인 분석:**
[왜 발생했는지, 어떤 파일·코드가 문제인지]

**영향 범위:**
- 수정 필요 파일: [파일 목록]
- 예상 변경 규모: [소/중/대]

**해결 계획:**
1. [1단계 작업]
2. [2단계 작업]
3. [검증 방법]

**예상 소요 시간:** [짧음/중간/김]
```

### Phase 2 — 실행 (Execution)

- 간단한 작업(한 파일, 명백한 오류 수정): 브리핑 후 사용자 응답 없어도 즉시 실행해도 됨
- 복잡한 작업(여러 파일, 아키텍처 변경): 브리핑 후 사용자의 명시적 승인 대기

### Phase 3 — 결과 보고 (Result Report)

실행 완료 후 반드시 다음을 보고한다:

- 변경한 내용 요약
- 검증 결과 (빌드/테스트 결과)
- 남은 후속 작업 (있다면)

---

## 금지 행동

| 금지 | 이유 |
|------|------|
| 파악 없이 바로 코드 수정 | 엉뚱한 파일 수정 위험 |
| 상황 설명 없이 명령어 실행 | 사용자가 무슨 일이 일어나는지 모름 |
| 계획 없이 단계별 보고 | 전체 그림을 파악할 수 없음 |
| 실행 완료 후 침묵 | 사용자가 결과를 확인할 수 없음 |

---

## 브리핑 간결함 원칙

- 브리핑은 **5줄 이내**로 핵심만 작성한다
- 뻔한 내용은 생략한다 (예: "파일을 열어보겠습니다" — 삭제)
- 모르는 것은 솔직히 "확인 필요"라고 명시한다
- 브리핑 자체가 너무 길면 안 쓴 것만 못하다

## 출력 예시

### ✅ 올바른 브리핑 예시

```
## 🔍 상황 파악

**현재 문제:** <project>/page.tsx JSX 주석 뒤 `}}` 중복 중괄호로 파싱 실패

**원인:** 주석 종료 후 닫는 중괄호(`}`)가 하나 더 있음 — `*/}}` → `*/}` 로 수정 필요

**영향 범위:** `<project-root>/src/app/<page>/page.tsx` 1개 파일, 1줄 수정

**계획:** 해당 줄 중괄호 제거 → 빌드 확인 → 커밋

바로 수정한다.
```

### ❌ 잘못된 예 (설명 없이 바로 시작)

```
(아무 설명 없이 파일 수정 시작...)
```
