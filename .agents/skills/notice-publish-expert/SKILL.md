# Notice Publish Expert — 웹 서비스 공지사항 관리 및 배포 전문가

웹 서비스 공지사항의 작성·등록과 운영 DB 배포·게시를 분리하여 안전하게 관리하는 워크플로를 정의한다.

## 0. 핵심 철학 및 라우팅·환경 분기 규칙 (CRITICAL)

### 0-1. 공지 관리 UI 기본 진입점
- 사용자가 "공지 수정", "공지 게시", "공지사항 관리" 등 UI 작업을 언급하면 일반 사용자 뷰가 아니라 관리자 공지 관리 화면(예: `/admin/bugs?tab=notice` 또는 프로젝트의 공지 어드민 경로)과 관련 컴포넌트를 기본 진입점으로 해석한다.

### 0-2. 등록과 배포의 분리

공지 원문 작성과 운영 DB 반영을 엄격히 분리한다. 작성 중인 미완성 내용이 사용자에게 조기 노출되거나 재배포 시 중복 등록되는 사고를 방지하기 위함이다.

| 사용자 요청 | 수행 범위 | 완료 보고 |
|---|---|---|
| 공지 작성·등록·수정·갱신, 릴리스 공지 준비 | 저장소 문서(`docs/notices/`)와 적용·검증·복구 쿼리 준비. DB 쓰기 없음 | 등록 완료, 배포 전 |
| 공지 배포·게시·발행, 공지를 운영에 반영 | 지정된 공지의 산출물을 프로덕션 DB에 적용하고 실제 조회 검증 | DB 반영 및 화면 검증 결과 |
| 로컬 공지에 적용·로컬 게시 | 명시된 로컬 DB에만 적용 | 로컬 적용 완료, 운영 미반영 |
| 코드 배포·버전 업·커밋·푸시 | 해당 작업만 수행. 공지 DB 적용을 자동 포함하지 않음 | 공지 등록·배포 상태를 별도로 표시 |
| 공지 관리 화면 수정 | 관리자 화면의 코드 수정 | 코드 변경 및 검증 결과 |

- **공지 배포 대상은 항상 운영(prod) DB가 기본이다 (MANDATORY)**: 사용자가 명시적으로 "로컬에 적용해"라고 지시하지 않는 한, 공지 등록·배포는 운영 DB를 대상으로 수행한다. 로컬 DB에 적용한 경우에는 "운영 DB에도 반영할까요?"라고 반드시 확인한다.
- “공지 등록하고 배포해”처럼 두 단계가 함께 명시되면 등록 산출물을 먼저 완성하고 배포까지 진행한다. 이미 승인된 범위를 재확인하지 않는다.
- “배포해”의 대상이 여러 미배포 공지 중 무엇인지 불명확하면 후보와 변경 내용을 먼저 준비하고 대상만 확인한다. 모든 초안을 일괄 적용하지 않는다.
- 공지 배포는 DB에 반영하는 작업이다. 사용자에게 공개되는 시점은 실제 조회 경로까지 확인한다. 커밋·태그·빌드 성공만으로 게시 완료라 하지 않는다.

### 0-3. 드래프트 워크플로우 (Draft Workflow)

1. **공지 작성 시 활성 드래프트 확인**:
   - `docs/notices/` 하위 폴더 중 `status: draft` 또는 `status: ready`인 `notice.md`가 있는지 확인한다.
   - 활성 드래프트가 있으면: 해당 버전의 공지에 새 항목을 추가한다. 버전을 다시 묻지 않는다.
   - 활성 드래프트가 없으면: 사용자에게 대상 버전(예: `v0.4.2`)을 먼저 확인한 후 `docs/notices/release-<version>/notice.md`를 생성하고 `status: draft`로 시작한다.

2. **드래프트 항목 누적**:
   - 같은 버전의 드래프트에 새 변경사항을 추가할 때는 기존 notice.md 본문 끝에 새 항목을 append한다.
   - 메타데이터의 `registered_at`을 최신 수정 시각으로 갱신한다.

3. **공지 배포 시 드래프트 소비**:
   - "공지 배포" 요청 시 현재 활성 드래프트의 내용을 기준으로 DB에 적용한다.
   - 배포 성공 후 notice.md의 `status`를 `published`로 변경하고 `published_at`을 기록한다.
   - 이후 새 공지 작성 요청이 오면 새 버전의 드래프트를 생성한다 (기존 published 폴더는 이력으로 보존).

4. **활성 드래프트 탐색 명령**:
   - 활성 드래프트를 찾는 방법: `grep -rl 'status: draft\|status: ready' docs/notices/*/notice.md`

## 1. 공지 작성 원칙: 사용자 관점 우선 (MANDATORY)

> **공지사항은 서비스 이용자가 읽는 것이다. 개발자/엔지니어 관점의 기술 용어를 절대 사용하지 않는다.**

### 1-1. 금지 표현 (개발자 용어)
| 절대 사용 금지 | 사용자 관점 대체 표현 |
|---|---|
| Prisma, ORM, Supabase, PostgreSQL, MySQL | "데이터 처리 시스템 개선" |
| API 라우트, REST, 엔드포인트 | "서버 연동 개선" |
| Cloudflare Workers, Docker, 컨테이너, 서버 | "배포 환경 안정화", "시스템 안정성 향상" |
| 리팩토링, 마이그레이션 | "시스템 개선", "기능 정비" |
| 컴포넌트, SSR, 렌더링 | "화면 표시 개선" |
| Git, 커밋, PR, 브랜치 | 언급하지 않음 |
| 타입체크, 린트, 빌드 | 언급하지 않음 |
| Zod, 스키마, 밸리데이션 | "입력 검증 강화" |

### 1-2. 작성 톤 & 구조
- **상투적 인사말·군더더기 서두 생략 (MANDATORY)**: "안녕하세요. XX 운영팀입니다" 같은 상투적 인사말이나 불필요한 미사여구는 사용하지 않고, 공지 제목 직후 변경 목적 및 핵심 요약부터 본론으로 바로 시작합니다.
- **친근하고 명확한 어조**: "~기능이 추가되었습니다", "~이(가) 개선되었습니다"
- **사용자가 체감할 수 있는 변화 중심**: 화면에서 보이는 것, 사용 흐름의 변화
- **번호 매기기**: 큰 카테고리는 📌 이모지 + 구분선, 세부 항목은 `1) 2) 3)` 형식
- **기술 변경은 체감 효과로 번역**: "DB 엔진 교체" → "데이터 안정성 및 응답 속도가 향상되었습니다"
- **chore/docs/내부 정비 커밋은 공지에 포함하지 않음**: 사용자에게 영향이 없는 변경은 생략

### 1-3. 공지 항목 선별 기준
| 포함 | 제외 |
|---|---|
| 새 기능 추가 (사용자가 직접 사용) | 내부 코드 정리 (리팩토링) |
| UI/UX 변경 (화면 구성 변경) | 문서 업데이트 (docs) |
| 버그 수정 (사용자가 겪던 문제 해결) | CI/CD 변경 |
| 성능 개선 (체감 가능한 경우) | 테스트 추가/변경 |
| 보안 강화 (사용자 데이터 보호) | 빌드 설정 변경 |

## 3. 등록 산출물과 누적 규칙

등록 시 [공지 원문 템플릿](assets/notice-template.md), [배포 이력 템플릿](assets/release-template.md)을 사용한다. 스키마 미확정 시 [쿼리 준비 템플릿](assets/query-plan-template.md)을 `query-plan.md`로 저장한다.

공지 하나에 안정적인 식별자 하나를 부여하고 `docs/notices/<공지키>/`에 보관한다. 예: `release-0.3.5`, `maintenance-2026-10-20`. 같은 미배포 공지를 수정할 때는 기존 폴더를 갱신한다. 다른 공지는 새 폴더로 만든다.

| 파일 | 내용 |
|---|---|
| `notice.md` | 사용자에게 보여줄 제목·본문과 운영 메타데이터 |
| `apply.sql` | 실제 스키마에 맞춘 등록 또는 수정 쿼리 |
| `verify.sql` | 공지 키·본문·대상·고정 여부·공개 상태를 검증하는 읽기 쿼리 |
| `rollback.sql` | 이번 적용만 취소하거나 직전 내용을 복원하는 쿼리 |
| `release.md` | 배포 이력과 검증 결과. 배포 전에는 미배포임을 표시 |

`notice.md` 상단 메타데이터에는 공지 키, 상태(`draft`, `ready`, `published`, `blocked`), 대상, 작성자, 고정 여부, 연계 버전·이슈, 수정 시각을 기록한다. 등록일과 실제 게시일을 구분하고 게시일은 적용 확인 후 기록한다. 내부 메타데이터와 배포 기록은 서비스 공지 본문에 넣지 않는다.

1. 기존 공지 문서와 중복 여부, 공지의 실제 사용자 영향 및 배포 여부를 확인한다.
2. 실제 테이블·열·고유 키·조회 경로를 코드와 스키마로 확인한다.
3. 원문을 작성하고, 현재 스키마로 실행 가능한 쿼리와 검증·복구 절차를 준비한다. SQL 문자열·개행은 안전하게 인코딩하고 문서와 쿼리 내용이 일치하는지 확인한다.
4. 운영 DB에는 쓰지 않는다. 로컬 실행도 요청 범위 또는 기존 승인 범위 안에서만 수행하며 실행했다면 로컬임을 명시한다.
5. 준비된 파일 경로, 등록 상태, 검증 여부와 배포 전임을 보고한다.

### DB 연동이 아직 없을 때
- 원문은 `notice.md`에 계속 저장한다. `blocked`로 표시하고 공지 테이블·영속 저장·조회 연동 중 무엇이 필요한지 기록한다.
- 확정되지 않은 테이블 이름으로 실행용 SQL을 만들지 않는다. 쿼리 설계 초안이 필요하면 문서의 코드 블록으로 저장하고 실행 불가임을 표시한다. 확정 스키마가 있어야 `apply.sql` 등의 실행 파일을 만든다.
- 미구현 테이블이나 고유 키를 만들기 위한 스키마 변경은 별도 작업으로 추적한다. 공지 등록만 요청한 경우 해당 개발을 자동으로 확대하지 않는다.

## 4. 쿼리의 품질 기준

- 안정적인 공지 키와 DB 고유 제약으로 재실행 중복을 막는다. 가능하면 대상 키에만 적용하는 upsert를 사용한다. 제목이나 목록 길이를 식별자로 쓰지 않는다.
- 새 공지 등록과 이미 게시한 공지 수정은 구분한다. 재시도에서 동일 내용은 변경하지 않으며 게시 시각·조회수 같은 운영 값도 보존한다.
- **핀 고정 자동 교체 (Pin Rotation)**: 새 공지를 등록(apply)할 때 `is_pinned = true`로 설정하면, 같은 트랜잭션 안에서 기존에 고정된 모든 공지의 `is_pinned`를 `false`로 해제한 뒤 새 공지만 고정한다. 항상 최신 공지 하나만 핀 고정 상태를 유지한다.
- SQL은 트랜잭션 안에서 대상 공지와 핀 교체 대상만 변경한다. 핀 교체 외의 다른 공지 삭제·조회수 초기화는 요청에 포함된 경우에만 수행한다.
- 문서 원문을 기준으로 SQL을 생성·갱신한다. 두 파일의 본문·대상·고정 상태가 어긋나면 배포하지 않는다.
- 적용할 문서와 쿼리의 커밋 또는 체크섬을 기록한다. 이미 배포한 산출물을 조용히 덮어쓰지 않고 다음 리비전과 수정 이력을 남긴다.
- 운영 DB 비밀값은 프로세스 환경으로 주입한다. 문서·SQL·로그에 인증값을 저장하지 않는다.

## 5. 배포와 완료 기준

1. 요청 대상 공지와 리비전을 정하고 `notice.md`, 쿼리, 복구 방법을 확인한다. 연계 기능이 실제 운영에 제공되는지도 확인한다.
2. 적용 전 대상 DB·스키마·현재 공지 값을 확인한다. 복구에 필요한 이전 값은 승인된 저장 위치에 보관한다.
3. 명시적으로 승인된 공지 배포 범위 안에서 준비한 쿼리를 실행한다. 일반 코드 배포나 전체 seed와 결합하지 않는다.
4. `verify.sql`로 운영 DB 값과 대상 행 수를 확인한다. 재실행 시 중복이나 게시일·조회수 손실이 없는지도 확인한다.
5. 관리자 화면과 실제 수신 대상 화면에서 새로고침·별도 세션 후 조회한다. DB 반영만 성공하고 화면에 안 보이면 두 결과를 구분해 보고한다.
6. `release.md`에 환경, 공지 키·리비전, 적용 시각, 산출물 체크섬 또는 커밋, DB 검증 결과, 화면 검증 결과, 실패·복구 여부를 기록한다. 검증되지 않은 항목은 미검증으로 남긴다.
7. DB 적용과 사용자 노출이 확인되면 `published`로 표시한다. 실패한 경우 미게시·부분 완료 상태를 보고하고 필요한 복구를 수행한다.

등록 산출물은 배포 후에도 저장소에 남긴다. 운영 DB는 실제 서비스 조회값을 제공하고 저장소는 검토된 원문과 변경 이력을 보존한다. 관리자 UI를 통한 편집이 생기면 해당 변경도 저장소에 대조·반영하여 다음 배포가 덮어쓰지 않게 한다.
