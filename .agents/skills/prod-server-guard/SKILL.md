# 프로덕션 서버 가드 (Prod Server Guard) — 운영 서버 접근 경고 스킬

## 언제 이 스킬을 사용하는가 (When to Invoke)

다음 조건 중 하나라도 감지되면 **예외 없이 즉시** 이 스킬을 활성화하십시오:

### 트리거 조건

| 분류 | 감지 예시 |
|----------|----------|
| **SSH / SCP 접근** | 운영 호스트/IP로의 `ssh` 접속, 운영 서버로의 `scp` 파일 전송 |
| **운영 Docker 제어** | 운영 컨텍스트에서의 `docker exec`, `docker restart`, `docker compose` 등 |
| **배포 명령어** | `./deploy.sh`, `docker build && push`, 운영 서버로의 CI/CD 트리거 |
| **운영 DB 기록 작업** | 운영 DB를 대상으로 하는 `pg_restore`, `psql` + DML/DDL 쿼리, `prisma migrate deploy` |
| **운영 파일 수정** | 원격 운영 서버에서의 `nano`, `vim`, `echo >` 명령어 실행 등 |
| **서비스 재시작** | 운영 호스트에서의 `systemctl restart`, `pm2 restart` 등 |

> **운영 서버 식별**: 운영 호스트 및 IP는 `.env.production`, `.env.prod`, 또는 프로젝트 환경 설정 파일 내의 `DATABASE_URL`, `SSH_HOST` 또는 유사한 변수들에 정의되어 있습니다. 사용자가 "prod 서버", "운영 서버", "운영 DB", "배포 서버" 등을 언급하면 운영 환경으로 간주합니다.

## 실행 절차 (Procedure)

### 1단계 — 대상 환경 감지

명령어를 실행하기 전에 대상을 식별합니다:

```bash
# 운영 환경 파일에서 호스트/IP 확인
grep -ri "host\|url\|ssh" .env.production .env.prod 2>/dev/null | head -10
```

명령어가 로컬 호스트(localhost)가 아닌 운영 호스트/IP를 가리키는 경우 2단계로 진행합니다.

### 2단계 — 필수 경고 배너 표시

**명령어를 실행하기 전에 항상 아래 경고 배너를 출력해야 합니다:**

```
🚨 [프로덕션 서버 접속 경고 / Production Server Access Warning]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔴  환경 / Environment : PRODUCTION (운영)
🖥️  대상 / Target      : {호스트명 또는 IP}
📋  작업 / Action      : {명령어 요약}
⚠️  위험도 / Risk      : {READ-ONLY | WRITE | DESTRUCTIVE}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⛔  실수로 프로덕션 데이터를 변경하면 서비스 장애가 발생할 수 있습니다.
    Unintended changes to production may cause service outages.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 3단계 — 위험 등급 분류

| 위험 등급 | 분류 기준 | 색상 표시 |
|------------|----------|-------|
| `READ-ONLY` | 단순 조회 목적의 `ssh`, `SELECT` 쿼리 등 | 🟡 노란색 (Yellow) |
| `WRITE` | 파일 수정, 서비스 재시작, INSERT/UPDATE 등 | 🟠 주황색 (Orange) |
| `DESTRUCTIVE` | `pg_restore`, `DROP`, `TRUNCATE`, `rm -rf` 등 데이터 파괴 작업 | 🔴 빨간색 (Red) |

**파괴적 작업(DESTRUCTIVE)**인 경우, 추가 경고 블록을 표시합니다:

```
💣 [파괴적 작업 추가 경고 / Destructive Action Extra Warning]
   이 작업은 되돌릴 수 없습니다. 백업 여부를 먼저 확인하세요.
   This action is IRREVERSIBLE. Verify backups exist before proceeding.
```

### 4단계 — 사용자의 명시적인 확인 대기

`ask_question` 도구를 사용하여 사용자에게 질문합니다:

**질문 내용:**
```
프로덕션 서버 [{호스트명}]에 다음 작업을 실행합니다:
  {실행할 명령어}

계속하시겠습니까?
```

**선택지:**
1. "네, 진행합니다"
2. "아니오, 취소합니다"

> **경고**: 사용자가 **선택지 1**을 선택하기 전까지는 절대로 명령어를 실행해서는 안 됩니다.
> 사용자가 취소를 선택하거나 질문을 건너뛰면 작업을 즉시 중단하고 이를 사용자에게 보고합니다.

### 5단계 — 실행 및 이력 기록

사용자 승인 후 명령어를 실행하고 결과를 보고합니다:

```
✅ [실행 완료 / Executed]
   작업: {실행한 명령어}
   시각: {타임스탬프}
   결과: {성공 | 에러}
```

명령어가 실패하면 사용자의 명시적인 추가 요청이 없는 한 임의로 재시도하지 말고 에러 내역을 그대로 출력하십시오.

## 환경 식별 규칙

| 소스 (Source) | 환경 라벨 (Environment Label) |
|--------|------------------|
| `.env.production` / `.env.prod` 호스트 | 🔴 PRODUCTION (운영) |
| `.env.test` / `.env.staging` 호스트 | 🟡 TEST / STAGING (테스트) |
| `localhost` / `127.0.0.1` | 🟢 LOCAL (가드 생략) |

- 포트 번호 차이 = 개별 환경으로 취급합니다.
- 사용자가 "prod" 또는 "운영"이라고 직접 언급하는 경우, 현재 `.env` 맥락과 무관하게 항상 PRODUCTION 환경으로 간주합니다.
- **로컬 DB/서버**는 이 가드 스킬의 적용 대상에서 제외됩니다.

---

## 절대 원칙 (Never Bypass)

1. **경고 배너를 먼저 표시하지 않고 운영 대상 명령을 실행하는 행위는 절대 금지됩니다.**
2. **동의를 자의적으로 해석하지 마십시오** — 응답이 없거나 모호한 경우 진행하지 않고 취소로 처리합니다.
3. **파괴적인 작업(DESTRUCTIVE)**을 수행할 때는 진행하기 전에 사용자가 백업의 존재 여부를 명확히 인지하고 있는지 반드시 확인해야 합니다.
4. **"빨리 해달라"**는 요청이 있더라도 이 가드를 생략할 수 없습니다. 신속성보다 안정성이 항상 우선입니다.

### ⛔ 독단적 결정 금지 (Do NOT Decide Alone)
- 어떠한 이유로든 경고 배너 표시 단계를 생략하는 행위 금지
- 파괴적 작업 수행 시 사용자의 명시적 확인 없이 자동으로 작업을 진행하는 행위 금지
- 호스트가 불분명할 때 임의로 "로컬(local)" 환경이라고 가정하는 행위 금지
