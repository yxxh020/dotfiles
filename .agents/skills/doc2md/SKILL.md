# 오피스 문서(docx) → 마크다운 변환 품질 스킬 (doc2md)

이 스킬은 워드(`.docx`) 등 오피스 문서를 텍스트 기반 마크다운(`.md`) 파일로 변환하고 구조를 재구성할 때 발동됩니다.

> [!IMPORTANT]
> **선행 스킬 참조 (Prerequisite)**
> 이 스킬을 수행하는 과정에서 반드시 **`create-markdown` 스킬**을 함께 참조하고 해당 포맷팅 규칙을 엄격하게 적용해야 한다.
> - 기존 `create-markdown` 스킬의 일반 규칙(물결표 범위 사용 금지, 볼드·따옴표 충돌 방지 등)을 기본으로 준수하며, 본 문서는 **문서 포맷 변환 시 발생하는 레이아웃 복원 및 구조화 절차**를 추가로 정의한다.

---

## 1. 변환 실행 및 초기 정리 (Conversion & Setup)

1. **변환 도구 활용**: 리눅스 환경에 설치된 `pandoc` 또는 관련 파싱 도구를 사용해 docx를 마크다운으로 1차 변환한다.
   ```bash
   pandoc -f docx -t markdown "원본문서.docx" -o "변환문서.md"
   ```
2. **원치 않는 이스케이프 문자 제거 (매우 중요)**:
   - 변환기(pandoc 등)가 마크다운 특수문자 충돌을 방지하기 위해 헤더 기호(`\#`), 대괄호 및 부등호(`\<`, `\>`), 대시 기호들(`\-\-\-`) 등의 앞에 과도하게 넣은 백슬래시(`\`) 이스케이프 문자를 적극적으로 찾아 제거한다. 이를 정리해야 정상적인 렌더링 및 이후 문서 치환 작업이 실패하지 않다.
   - ❌ **잘못된 예 (렌더링 방해 및 치환 매칭 실패 원인):**
     - `\# 데이터 참조`
     - `\< 표1. 수익모델의 예시 \>`
     - `\-\-\-\-\-\-\-\-\-\-\-\-\-\-\-\-\-\-`
   - ✅ **올바른 예 (깨끗한 마크다운):**
     - `# 데이터 참조`
     - `< 표1. 수익모델의 예시 >`
     - `------------------`

---

## 2. 표(Table) 가독성 극대화 및 GFM 변환

docx 문서의 표는 변환 시 깨지거나 복잡한 그리드 테이블(Grid Table) 형태로 변환되어 가독성이 심각하게 떨어지는 경우가 많다.

- **그리드 테이블 포착 시 재구성**:
  - 변환 결과물에 `----`와 `|`로 구분된 길고 무너진 그리드 표가 발견되면, 즉시 **GitHub Flavored Markdown (GFM) 표 형식**으로 전면 재구성한다.
  - 가로 폭이 너무 길어 컬럼이 밀리는 경우, 핵심 단어 위주로 텍스트를 축약하거나 단위를 통일하여 한눈에 표가 들어오도록 다듬다.
- **예시 (올바른 GFM 표 구조):**
  ```markdown
  | 구분 | 항목 A | 항목 B |
  |---|---|---|
  | **내용 1** | 상세 설명 | 상세 설명 |
  ```

## 3. 텍스트 플로우의 Mermaid 도표화 (Mermaid Diagramming)

변환 과정에서 텍스트로만 나열된 **프로세스, 작업 흐름, 관계도, 시퀀스** 등은 가독성이 매우 떨어집니다. `use-mermaid` 스킬과 연계하여 적극적으로 Mermaid 다이어그램을 추가한다.

- **적용 대상**:
  - `A 단계 -> B 단계 -> C 단계` 와 같은 단계별 작업 흐름
  - 사용자, 플랫폼, 수행자 간의 요청/응답 상호작용 (시퀀스)
  - 기존 업무 프로세스와 플랫폼 도입 후의 개선 프로세스 대비
- **도표 유형 선택 가이드**:
  - **순서도(Flowchart TD/LR)**: 조건 분기나 병렬 처리가 있는 시스템 아키텍처 및 업무 흐름
  - **시퀀스 다이어그램(Sequence Diagram)**: 여러 주체(의뢰인, 플랫폼, 수행자 등) 간의 시간 순서에 따른 상호작용 및 수수료/데이터 정산 흐름
- **작성 및 가독성 규칙**:
  - **가로폭 과다 방지 (위아래 2줄 배치)**: 기존 프로세스와 플랫폼 지원 프로세스 등 여러 흐름을 하나의 다이어그램에 병렬(subgraph 나열) 배치하면 가로폭이 지나치게 길어져 가독성이 극도로 악화됩니다. 반드시 **각각의 흐름을 독립된 Mermaid 코드 블록으로 쪼개서 세로로 순서대로 나열**하십시오.
  - **문법 오류 방지**: Mermaid 라벨 내부에 특수문자(괄호 등) 및 줄바꿈(`\n`) 사용 시 구문 에러 방지를 위해 반드시 큰따옴표(`""`)로 감쌉니다. (예: `A["상태 (상세)"]`, `B1["기존 프로세스\n(자가 수행)"]`)

## 4. 품질 검증 체크리스트 (Verification Checklist)

변환 완료 후 최종 보고 전에 다음 사항을 점검해야 합니다:
1. **렌더링 깨짐 유무**: 마크다운 뷰어에서 표가 올바르게 사각형 그리드로 표현되는가?
2. **Mermaid 구문 오류**: 다이어그램 렌더링 시 구문 에러(Syntax Error) 없이 정상 표시되는가?
3. **원본 삭제**: 변환이 성공적으로 완료되었음을 검증한 후 사용자의 요청에 따라 원본 docx 파일이 깨끗이 삭제(`git rm` 혹은 `rm`)되었는가?
