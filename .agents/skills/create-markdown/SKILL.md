# 마크다운 품질 통합 스킬 (Markdown Quality Skill)

이 스킬은 마크다운 문서를 다루는 세 가지 상황에서 발동됩니다:
1. **마크다운 생성·편집 시**: 렌더링 버그를 유발하는 포맷팅 패턴(취소선, 볼드 충돌, 리스트 내 들여쓰기 HTML 코드블록 오인식)을 방지한다.
2. **이미지 및 캡처 삽입 시**: 로컬과 GitHub 웹 모두에서 깨지지 않는 상대 경로, 폴더 구조, kebab-case 네이밍 및 체크리스트 표준을 준수한다.
3. **PDF 변환 시**: `marker_single`을 활용해 복잡한 PDF를 구조화된 마크다운으로 변환한다.

## Part 1. 마크다운 포맷팅 품질 규칙 (Formatting Rules)

Obsidian, GitHub 등 다양한 마크다운 파서에서 발생하는 렌더링 버그를 방지한다.

### 1. 취소선 및 볼드 파괴 방지 (Strikethrough & Bold Destruction Prevention)

연속된 물결표(`~`) 또는 앞뒤 공백 없는 물결표는 마크다운 파서에서 의도치 않은 **취소선(Strikethrough)**을 유발하며, 볼드(`**`)와 겹칠 경우 **볼드 문법을 완전히 파괴하여 별표(`**`)가 그대로 노출되는 렌더링 참사**를 일으킵니다.

- **원인 및 파괴 메커니즘:**
  - CommonMark, GFM, 채팅 UI 뷰어는 문장/문단 내에 떨어져 있는 두 개의 물결표(`~단어1~ ... ~단어2~`)를 하나의 취소선 쌍으로 인식하여 그 사이의 모든 텍스트를 취소선으로 그어버립니다.
  - 특히 취소선 구간이 볼드(`**`) 태그를 관통하면(`5~10명이 ... **월 0원~3만 원**`), 여는/닫는 `**` 짝이 깨져 볼드가 해제되고 별표(`**`)가 화면에 그대로 노출됩니다.
- **수량·금액·기간·인원·회차 등 모든 범위 표기 시 공백 없는 `~` 사용 절대 금지:**
  - ❌ 잘못된 예 (취소선 발생 및 볼드 파괴):
    - `5~10명`, `0원~3만 원`, `800만~1,200만 원`
    - `4~6주`, `25원~35원`, `1~3회차`
    - `20~24px`, `40~45 chars`
  - ✅ 올바른 표준 표기 (하이픈 `-` 또는 공백 포함 물결표 ` ~ ` 또는 한글 `에서 ~까지`):
    - `5-10명` 또는 `5 ~ 10명` (가장 권장)
    - `0원 - 3만 원` 또는 `0원 ~ 3만 원`
    - `800만 - 1,200만 원` 또는 `800만 ~ 1,200만 원`
    - `4-6주` 또는 `4 ~ 6주`
    - `25원 - 35원` 또는 `25원 ~ 35원`
    - `1-3회차` 또는 `1 ~ 3회차`
    - `20-24px`, `20 to 24px`, `40 to 45 chars`
- **완료 항목 표기 시 리터럴 취소선(`~~...~~`) 지양 및 대체 표준 준수:**
  - 작업 완료, 해결된 이슈 등을 표기할 때 본문이나 리스트 전체를 `~~...~~`로 감싸면, 내부의 인라인 코드(`code`), 볼드(`**`), 링크 전체에 가로선이 그어져 가독성이 심각하게 저하됩니다.
  - ❌ 잘못된 예 (가독성 훼손):
    - `~~**DB 차원 표본 대조**~~ → ✅ **완료**`
    - `~~프로젝트명(`title` vs `PROJECT_TITLE`) 유사도 분석~~`
  - ✅ 올바른 표준 표기 (체크박스 `[x]`, 상태 뱃지 `✅ 완료` 접두사, 또는 완료 섹션 분리):
    - `1. [x] **DB 차원 표본 대조 (개발자 즉시 수행)** (2026-10-14 완료)`
    - `- ✅ **완료**: 프로젝트명(`title` vs `PROJECT_TITLE`)의 문자열 유사도 분석`
- **리터럴 물결표 출력 시 이스케이프 또는 공백 필수:**
  - 반드시 물결표 기호를 단독으로 출력해야 할 경우 반드시 이스케이프(`\~`)하거나 앞뒤 공백을 둔 형태(` ~ `)로만 작성한다.
- **AI 채팅 응답(Chat Response) 무조건 강제 적용:**
  - 마크다운 문서 파일 생성·수정뿐만 아니라, **사용자와 대화하는 모든 AI 채팅 응답에서도 예외 없이 100% 적용**한다.

### 2. 볼드·따옴표 충돌 방지 (Bold-Quote Collision)

볼드 애스터리스크(`**`) 바로 안에 따옴표(`"` 또는 `'`)가 오면(`**"` 또는 `**'` 형태) Obsidian, GitHub, 그리고 구글 문서(Google Docs)의 마크다운 파서가 문법 경계를 제대로 인식하지 못해 볼드가 렌더링되지 않거나 별표(`**`)가 그대로 노출되는 심각한 버그가 발생한다.

- **원인:** `**"` 또는 `**'` 패턴 시작 시 닫는/열는 강조 경계 오인식 (특히 Google Docs '마크다운으로 붙여넣기' 시 100% 별표 노출 버그 발생)
- **권장 해결책 (따옴표를 볼드 바깥에 배치):**
  - ❌ 잘못된 예: `**"옵시디언 워크숍"**`, `**'Orca'**다` (볼드체 렌더링 깨짐 및 별표 노출)
  - ✅ 올바른 예: `"**옵시디언 워크숍**"`, `'**Orca**'다` (정상 렌더링 - 가장 권장)
- **대안 해결책:**
  1. **HTML 태그 사용 (`<b>` 또는 `<strong>`):** 따옴표까지 모두 굵게 표현 시 100% 안전
     - 예: `<b>"옵시디언 워크숍"</b>`
  2. **낫표(`『 』`) 또는 꺾쇠(`< >`) 활용:** 큰따옴표 대신 문장 부호 사용
     - 예: `**『옵시디언 워크숍』**`, `**<옵시디언 워크숍>**`
  3. **따옴표 이스케이프 (`\"`):**
     - 예: `**\"옵시디언 워크숍\"**`

### 3. 리스트 하위 들여쓰기 HTML 코드블록 오인식 방지 (Indented HTML Code Block Collision)

번호 매기기(`1.`, `2.`) 또는 글머리 기호(`-`, `*`) 리스트 하위에서 들여쓰기(공백 4칸 이상)와 함께 `<p>`, `<img>`, `<div>` 등 HTML 태그를 작성하면, 마크다운 파서(CommonMark)가 이를 **들여쓰기 코드 블록(Indented Code Block)**으로 해석하여 태그 문자열이 코드 박스 형태로 노출되는 심각한 렌더링 버그가 발생한다.

- **원인:** 리스트 하위 공백 4칸 이상 들여쓰기된 행을 파서가 `<pre><code>` 블록으로 자동 변환함
- **권장 해결책 (순수 표준 마크다운 문법 사용):**
  - 리스트 항목 내부에서는 들여쓰기 HTML 태그 대신 항상 **순수 표준 마크다운 문법**을 사용한다.
  - ❌ 잘못된 예:
    ```markdown
    1. 새 프로젝트 추가:
       <p align="center">
         <img src="./images/step1.png" width="300" />
       </p>
    ```
  - ✅ 올바른 예 (순수 마크다운 이미지 문법 + 빈 줄 분리):
    ```markdown
    1. 새 프로젝트 추가:

       ![새 프로젝트 추가](./images/step1.png)
    ```
- **대안 해결책 (독립 문단 레벨 작성):**
  - 정렬이나 크기 제어를 위해 HTML 태그(`<p align="center">`)를 반드시 써야 할 경우, 리스트 하위 들여쓰기 형태를 피하고 **리스트 밖(들여쓰기 0칸)의 독립 문단**으로 작성한다.

### 4. 텍스트 박스 드로잉(ASCII Box) 금지 및 시각화 표준 (No ASCII Box-Drawing)

코드 블록(```) 내에서 `┌─┐`, `│`, `└─┘`, `+--+`, `|` 같은 텍스트 선 문자로 사각 박스 레이아웃을 그리면 안 됩니다. 한글 및 이모지, 글꼴 너비(전각/반각) 차이로 인해 뷰어마다 줄바꿈과 정렬이 심각하게 깨지는 렌더링 결함이 발생한다.

- **원인:** 한글, 공백, 영문, 이모지의 문자 너비(폰트별 가변폭 및 전각 문자 너비) 불일치로 인해 오른쪽 테두리선(`│`)이 지그재그로 깨짐
- **규칙:**
  1. 구조화된 다이어그램이나 시각적 박스가 필요할 때는 **Mermaid 다이어그램 (`mermaid`)**을 사용한다.
  2. 단순 정보 요약이나 카드 형태가 필요할 때는 박스를 그리지 말고 **인용 블록(`>`), 마크다운 표(Table), 또는 글머리 기호 리스트**를 사용한다.
  3. 텍스트 기반 사각 상자/박스 테두리는 절대 직접 그리지 않다.
- ❌ 잘못된 예 (ASCII 박스 그리기):
  ```text
  ┌───────────────────────────────┐
  │ 📋 이슈 #12            🟢 열림 │
  │ 제목: 팀 소개 페이지 초안 작성 │
  └───────────────────────────────┘
  ```
- ✅ 올바른 예 (Mermaid 서브그래프 또는 마크다운 인용구/표 활용):
  > 📋 **이슈 #12** `🟢 열림`  
  > * **제목**: 팀 소개 페이지 디자인 초안 작성  
  > * **담당자**: AI 비서  
  > * **라벨**: `긴급🔴`, `디자인🟡`

### 5. Mermaid 및 테이블 내 HTML 태그(`<br>`, `<b>`) 사용 금지 (No HTML Tags in Diagrams/Tables)

Mermaid 노드 라벨(`["..."]`)이나 마크다운 표(Table) 셀 내에 `<br>`, `<b>`, `<strong>` 등의 HTML 태그를 직접 삽입하면 안 됩니다. 마크다운 파서 및 뷰어 환경(Obsidian, GitHub, VS Code 등)에 따라 태그가 렌더링되지 않고 문자열 그대로 노출되는 심각한 시각적 결함이 발생한다.

- **원인:** 다이어그램 엔진 및 일부 마크다운 파서의 HTML 새니타이징 및 이스케이프 정책 차이
- **규칙:**
  1. Mermaid 노드 라벨에는 줄바꿈 태그(`<br>`)를 쓰지 않고, 핵심만 담은 **간결한 단일 문구**로 작성하거나 **여러 서브 노드로 분리**한다.
  2. 표(Table) 셀 내에서 줄바꿈이 필요할 때는 `<br>` 대신 **슬래시(`/`) 구분자 사용**, **행(Row) 분리**, 또는 **리스트 형태**로 전환한다.
- ❌ 잘못된 예: `G["메뉴 찾기<br><b>마우스 클릭</b>"]`
- ✅ 올바른 예: `G["메뉴 찾기 및 직관적인 마우스 클릭"]` 또는 서브 노드 분리

### 6. 외부 문서 도구(Google Docs 등) 호환을 위한 프롬프트/예시 블록 표준화

긴 질문 프롬프트, 템플릿, 예시 문구를 작성할 때 마크다운 코드 블록(```) 내에 소제목과 본문을 통째로 감싸면 안 됩니다. Google Docs, 워드 등 외부 문서 도구로 복사·붙여넣기 시 코드 블록 경계선이 사라지고 줄바꿈이 깨져 일반 평문 덩어리로 뭉개지는 현상이 발생한다.

- **규칙:**
  1. 재사용 가능한 프롬프트나 예시문은 코드 블록(```) 대신 **소제목(`####`) + 인용 블록(`>`) 구조**를 기본으로 사용한다.
  2. Google Docs로 문서를 이관할 때는 원문 텍스트 복사 대신, **마크다운 뷰어의 렌더링 화면(Preview)에서 복사-붙여넣기(HTML 복사)**하거나 구글 문서의 `마크다운으로 붙여넣기` 메뉴를 사용하도록 안내한다.
- ❌ 잘못된 예 (Google Docs 붙여넣기 시 뭉개짐):
  ```markdown
  ```markdown
  [지시 프롬프트 1]
  "구글 시트로 출석부를 만들어줘..."
  ```
  ```
- ✅ 올바른 예 (Google Docs 붙여넣기 시 공식 인용문 상자로 깔끔하게 변환됨):
  #### 💬 프롬프트 1 — 출석부 생성
  > "구글 시트로 출석부를 만들어줘..."

### 7. 기술 가이드 작성 시 난이도별 분기(CLI vs GUI) 및 택일(XOR) 명시 규칙

설치나 환경 설정 안내 문서를 작성할 때, CLI(터미널 명령어)와 GUI(데스크톱 프로그램)가 나열되면 초보자는 둘 다 해야 하는 것으로 오인하여 진입장벽을 느낍니다.

- **규칙:**
  1. 복수의 설치/실행 방법이 존재할 경우, 서두에 반드시 **"둘 다 할 필요 없이 하나만 선택하면 된다"는 택일(XOR) 관계**를 명시한다.
  2. 비개발자/초보자를 위한 추천 경로(예: GUI 데스크톱 앱)가 있다면, 고급자용 경로(예: CLI 명령어) 상단에 **"초보자는 이 단계를 건너뛰고 바로 다음 단계로 이동하라"는 건너뛰기 안내 상자**를 최우선 배치한다.

### AI 적용 범위

모든 AI 에이전트는 다음 작업 시 위 규칙을 무조건 적용합니다:
- `*.md` 파일 작성 및 수정
- 채팅 응답에 마크다운 포함 시
- 프로젝트 문서 업데이트 시

## Part 2. 마크다운 이미지 삽입 및 캡처 표준 (Image & Screenshot Guide)

마크다운 문서(`output/*.md`, `docs/*.md`) 및 슬라이드(`output/5-lecture-slides.md`)에 이미지(스크린샷, UI 캡처, 다이어그램)를 삽입할 때, **로컬 뷰어(Orca IDE, 옵시디언, Marp)와 GitHub 웹 저장소 모두에서 이미지가 깨지지 않도록** 아래 표준을 엄격히 적용한다.

### 1. 이미지 디렉터리 구조 및 저장 위치
- 배포용 문서 및 강의안과 동일한 계층의 **`images/`** 전용 폴더 내에서 관리한다.
  - `output/images/` : 학생 배포용 이미지 저장소
  - `docs/images/` : 내부 관리용 이미지 저장소 (필요 시)
- ⚠️ **루트 디렉터리 이미지 저장 금지**: 이미지는 프로젝트 루트 디렉터리에 직접 저장하지 않고, 반드시 해당 문서를 포함하는 폴더 하위의 `images/` 디렉터리 내에서 관리한다.

### 2. 경로 참조 규칙: '문서 기준 상대 경로' 원칙
- 항상 문서 기준 상대 경로를 사용합니다:
  - `output/` 문서에서 참조 시: `![대체텍스트](./images/파일명.png)`
  - ❌ **절대 경로 금지**: `![캡처](C:/Users/.../images/test.png)`
  - ❌ **저장소 루트 기준 경로 금지**: `![캡처](/output/images/test.png)`

### 3. 이미지 파일 네이밍 규칙
- **영문 소문자 + 하이픈(`-`) 조합 (kebab-case)**:
  - ✅ `orca-new-project-01-sidebar.png`, `obsidian-graph-view.png`
  - ❌ `실습 2-1 캡쳐.PNG` (한글/공백 URL 인코딩 깨짐 위험)
  - ❌ `Image_01 (1).jpeg` (공백, 괄호, 대문자 금지)
- **식별 가능한 접두어 포함**: `ch02-...`, `lab-2-1-...`, `orca-...`
- **확장자**: 스크린샷은 텍스트 가독성을 위해 **`.png`** 또는 최적화된 **`.webp`** 사용

### 4. 용도별 이미지 문법
1. **기본 마크다운 (강의안·실습서 기본 - 가장 권장)**:
   ```markdown
   ![AI 비서 모델 선택 버튼 위치](./images/model-selection.png)
   ```
2. **독립 문단 HTML 태그 (크기 및 정렬 제어 필요 시)**:
   ```html
   <p align="center">
     <img src="./images/ide-layout.png" alt="IDE 화면" width="650" />
   </p>
   ```
   *(주의: 리스트 하위에서는 절대 사용 금지)*
3. **Marp 슬라이드 전용 디렉티브 (`output/5-lecture-slides.md`)**:
   ```markdown
   ![w:600px](./images/github-fork-button.png)
   ![center h:400px](./images/obsidian-graph-view.png)
   ```

### 5. 수강생 친화적 UI 캡처 팁
- **핵심 영역 크롭 (Close-up Crop)**: 전체 화면 캡처 대신 클릭 대상 버튼 주변 영역을 집중 크롭한다.
- **시각적 강조 및 단계 표기**: 클릭 대상에 테두리 상자 또는 `1️⃣`, `2️⃣` 숫자 뱃지를 표기한다.
- **민감 정보 마스킹**: 개인/회사 프로젝트명, 토큰, 비밀번호 등은 블러 또는 모자이크 처리한다.
- **용량 최적화**: 가로 800~1200px 수준으로 최적화한다.

## Part 3. PDF → 마크다운 변환 절차 (PDF Conversion)

사용자가 "이 PDF를 변환해서 읽어줘" 또는 "복잡한 PDF 문서의 텍스트를 추출해 줘"라고 요청할 때 발동됩니다.

### 변환 절차

1. **PDF 변환 실행**: `marker_single` 명령어로 PDF를 `/tmp`로 변환한다.
   ```bash
   marker_single "/경로/원본문서.pdf" --output_dir /tmp/
   ```
2. **변환 대기**: 파일 크기에 따라 수십 초 ~ 수 분 소요. 완료까지 대기한다.
3. **결과물 탐색**: `/tmp/원본문서/원본문서.md` 경로에 마크다운 파일이 생성됩니다.
4. **마크다운 읽기**: `view_file` 도구로 생성된 `.md` 파일을 읽어 내용을 파악한다.
5. **요약 보고**: 문서 구조와 핵심 내용을 사용자에게 보고한다.

### 주의 사항

- `marker_single` 최초 실행 시 OCR·레이아웃 분석 모델(PyTorch 기반)을 다운로드하므로 초기 로딩이 길 수 있다.
- 변환 결과 폴더에는 `.md` 파일 외에 PDF에서 추출된 이미지도 함께 저장됩니다.
- RAM/CPU를 많이 사용하므로 한 번에 하나의 PDF만 변환하도록 제어해라.
- 변환된 마크다운 출력 시에도 **Part 1과 Part 2의 포맷팅 및 이미지 규칙을 동일하게 적용**한다.
