# 체계적 디버깅 워크플로

복잡한 버그, 배포 오류, DB 연동 오류, 라우팅 문제 등을 디버깅할 때 **반드시 따라야 하는 4단계 방법론**을 정의한다.

## 핵심 철칙
- **절대 짐작으로 코드를 고치지 않는다.**
- **증상만 가리거나 땜질식 처방을 내리지 않는다.**
- 오류가 발생하면 아래 4단계를 순서대로 밟아 분석 결과를 먼저 사용자에게 보고하고, 승인 후 코드를 수정한다.

## 4단계 디버깅

### 1단계: 로그 확보 및 현상 명확화
- 섣불리 코드를 분석하거나 짐작하지 않는다. 먼저 **충분한 정보(로그)를 확보**하는 것이 최우선이다.
- 터미널 명령어(`docker logs`, `journalctl`, `tail` 등)나 `grep_search`를 통해 실존하는 에러 로그를 수집한다.
- 기존 로그가 부족하면 소스 코드에 `console.log`를 적극 삽입하거나, 셸 스크립트에 디버그 옵션(`set -x`)을 임시로 주입하여 충분한 로그를 직접 생성한다.

### 2단계: 근본 원인 추적
- 에러가 표출된 표면적 위치가 아닌, **에러가 탄생한 최초의 지점(근본 원인)**을 역추적한다.
- 예: "DB 저장 실패"가 현상이라면, DB 스키마·ORM 파라미터·프론트엔드 Payload 중 어디가 원인인지 API 계층을 따라 추적한다.

### 3단계: 해결책 설계 및 다중 방어
- 버그 라인을 고치는 것을 넘어, **유사한 상태에서 시스템이 죽지 않도록 방어 체계**를 함께 설계한다.
- **필수 포함 요소:**
  1. `try/catch` 등 예외 처리 보강
  2. 원인 파악이 쉽도록 **맥락이 담긴 구체적 에러 로그** 추가
  3. 잘못된 파라미터나 Null 값 엣지 케이스 방어 로직 추가

### 4단계: 상태 기반 검증
- 수정 후 "기다리면 될 것이다"라는 접근을 지양한다.
- API가 200을 반환하는지, DB 쿼리가 성공했는지 **확실한 조건 기반으로 검증하는 명령어를 실행하여 증거를 확보**한다.
