# 🔄 프로젝트 개선 사이클

코드베이스를 점검하여 이슈를 발견·등록하고, 해결한 뒤, 문서를 정리하는 과정을 새로운 이슈가 발견되지 않을 때까지 반복한다.

## 🎯 목표

```
코드 건강 점검 → 이슈 발견 → 해결 → 문서 정리 → 반복
(새로운 이슈가 없을 때까지)
```

---

## 📋 운영 흐름

### 사이클 구조

```
0️⃣ [코드 건강 측정]
   - 타입 체크, 린트, 테스트, 빌드 실행
   - 감점 항목 목록 도출 → Step 1의 입력

1️⃣ [코드베이스 감시 → 이슈 등록]
   - 루브릭 감점 항목 + 코드 스캔 결과 → gh issue create
   - 결과: 새 이슈 목록 수집

2️⃣ [이슈 계획 및 해결]
   - /issues-plan-and-resolve 워크플로우 실행
   - 결과: 이슈 닫힘 + 커밋

3️⃣ [문서 감사]
   - AGENT.md, README.md 등 문서 현황 반영 및 중복 제거
   - 결과: 문서 최신화 커밋

4️⃣ [종료 조건 판단]
   → 새 이슈 있음: 2️⃣로 돌아간다
   → 새 이슈 없음 + 건강도 미흡(75점 미만): 감점 항목 이슈화 후 계속
   → 새 이슈 없음 + 건강도 양호(75점 이상): 완료 ✅
```

---

## 🔎 Step 0: 코드 건강 측정

아래 명령을 프로젝트 개발 환경에 맞춰 순서대로 실행하고 결과를 기록한다. (예: frontend 등 소스 폴더가 별도로 있는 경우 해당 폴더에서 실행)

```bash
# 1. 타입 체크 (오류 수)
cd [FRONTEND_DIR] && npx tsc --noEmit 2>&1 | tail -5

# 2. 린트 (경고/오류 수)
cd [FRONTEND_DIR] && npx eslint src --ext .ts,.tsx --max-warnings 0 2>&1 | tail -10

# 3. 테스트 실행
cd [FRONTEND_DIR] && npm test -- --passWithNoTests 2>&1 | tail -10

# 4. 빌드 검증
cd [FRONTEND_DIR] && npm run build 2>&1 | tail -10
```

**측정 결과 → 점수 환산 기준**

| 항목 | 100점 기준 | 감점 조건 |
|------|-----------|----------|
| 타입 오류 | 0개 = 만점(25점) | 오류 1개당 -2점 |
| 린트 오류 | 0개 = 만점(20점) | 오류 1개당 -2점 |
| 테스트 통과율 | 100% = 만점(25점) | 실패 1건당 -5점 |
| 빌드 성공 | 성공 = 만점(30점) | 실패 시 -30점 |

**75점 이상이면 건강도 양호, 미만이면 미흡.**

---

## 🕵️ Step 1: 코드베이스 감시 → 이슈 등록

**`github-issue` 스킬 기준으로 이슈를 등록한다.**

### 1-1. 감시 체크리스트

다음 항목을 순서대로 점검한다:

- **타입 안전성**: `tsc` 오류, `any` 남용, 누락된 타입 정의
- **린트 위반**: ESLint 오류, 사용되지 않는 임포트, console.log 잔류
- **테스트 누락**: 핵심 기능(API 라우트, 유틸 함수)에 테스트 없음
- **성능 이슈**: 불필요한 re-render, 누락된 메모이제이션, N+1 쿼리
- **보안 취약점**: 미검증 입력, 노출된 시크릿, CSRF/XSS 위험
- **문서-코드 불일치**: AGENT.md에 명시된 스펙과 실제 구현 불일치
- **미완성 TODO/FIXME**: 소스코드 내 `TODO`, `FIXME` 주석 잔류
- **아키텍처 위반**: 단일 루트 원칙 위반, 환경변수 중복 정의

### 1-2. 이슈 등록 규칙

```bash
# 버그 이슈 예시
gh issue create \
  --title "fix: [영역] 문제 설명" \
  --body "## 현상\n...\n\n## 원인\n...\n\n## 제안 해결책\n..." \
  --label "bug"

# 개선 이슈 예시
gh issue create \
  --title "feat: [영역] 개선 설명" \
  --body "## 목적\n...\n\n## 구현 방향\n..." \
  --label "enhancement"
```

> **중복 방지**: 등록 전 `gh issue list --state open` 으로 유사 이슈 존재 여부를 반드시 확인한다.

### 1-3. 종료 조건 판단

```
이슈 등록 후:
  - 새 이슈가 1개 이상 등록됨 → Step 2로 진행
  - 이슈 없음 + 건강도 75점 미만 → 감점 항목을 이슈화 후 Step 2로 진행
  - 이슈 없음 + 건강도 75점 이상 → 사이클 완료 ✅
```

---

## 🛠️ Step 2: 이슈 계획 및 해결

**`/issues-plan-and-resolve` 워크플로우를 실행한다.**

핵심 원칙 요약:
- 분석은 병렬, 구현은 순차
- 실행 순서: 테스트 인프라 → 단순 수정 → 의존성 순서 → 독립 이슈 → 리팩토링 → 문서
- 커밋 게이트: 테스트 종료 코드 0일 때만 커밋
- 이슈 종료: `gh issue close N` + 검증 요약 포함

---

## 📝 Step 3: 문서 감사

**`doc-audit-expert` 글로벌 스킬 기준으로 문서를 정리한다.**

### 3-1. 감사 대상

| 문서 | 점검 내용 |
|------|----------|
| `AGENT.md` | 스킬/워크플로우 인벤토리 최신화, 기술 스택 정확도 |
| `SOUL.md` | 로드맵 반영 여부 |
| `README.md` | 개요 및 최신 상태 반영 여부 |
| `.agent/rules-project.md` | 규칙 적시성, 중복 항목 제거 |
| `.agent/workflows/*.md` | 워크플로우 설명과 실제 동작 일치 여부 |
| `.agent/skills/*/SKILL.md` | 스킬 설명과 현재 프로젝트 환경 일치 여부 |

### 3-2. 문서 커밋

```bash
git add AGENT.md SOUL.md README.md
git commit -m "docs: 사이클 #N 후 문서 정리"
```

---

## 🔁 반복 판단

Step 3 완료 후 Step 0부터 재측정하여 종료 조건을 재판단한다.

```
새 사이클 시작 기준:
  - 이전 사이클에서 발견된 이슈가 1개라도 있었다면 → 재측정 필수
  - 이전 사이클에서 이슈 0개 + 건강도 75점 이상 → 완료 ✅
```

---

## 🎛️ 실행 옵션

### 1. 사이클 제한
```
"프로젝트 개선 사이클 (최대 3회)"
```

### 2. 범위 제한
```
"프로젝트 개선 사이클 (보안만)"
"프로젝트 개선 사이클 (타입 체크만)"
```

### 3. 수동 승인 모드
```
"프로젝트 개선 사이클 (수동 승인)"
```
각 이슈 해결 전 사용자 확인을 받는다. `/issues-plan-and-resolve`의 Phase 2 이후 자동 진행을 멈춘다.

## 📊 상태 추적 예시

```
Cycle 1:
  ✅ 건강 측정    → 타입 오류 3건, 린트 5건 (점수: 62점)
  ✅ 이슈 등록    → #12, #13, #14 등록
  ✅ 이슈 해결    → #12, #13, #14 종료
  ✅ 문서 감사    → AGENT.md, README.md 업데이트

Cycle 2:
  ✅ 건강 측정    → 타입 오류 0건, 린트 0건 (점수: 90점)
  ✅ 이슈 등록    → 새 이슈 없음
  🎉 사이클 완료

최종:
  총 사이클:  2회
  해결 이슈:  3개
  문서 커밋:  2회
  최종 건강도: 90점 (양호)
```

## 🔐 안전 장치

- 매 사이클 시작 시 열린 이슈 수와 건강도 점수를 기록한다.
- 최대 사이클 수(기본 5회)를 초과하면 즉시 중단하고 현황을 보고한다.
- 같은 이슈가 2 사이클 연속으로 재등록되면 경고하고 사용자 승인을 받는다.
- 빌드 실패가 발생하면 **즉시 중단**하고 해결 후 재개한다.
- 모든 수정사항은 `/commit` 또는 `/commit-all` 워크플로우로 기록한다.
